# Lua API: `omegga.brickadia` (`BR`)

```lua
local BR = require("omegga.brickadia")   -- any mod; the bridge's `exec` has it as the global BR
```

The `BR` helpers and recipes were all run on a server. All of them touch UObjects, so call them
on the game thread: from `Omegga.handle` handlers, `exec`, `ExecuteInGameThread` or `RegisterHook`
callbacks, never directly from a `LoopAsync` body.

Values that are opaque engine structs travel as Lua strings of raw bytes: a brick handle is 8
bytes, a builder 0x38, a port ref 8, a wire value 0x28. Treat them as tokens; layouts are in
[brickadia-internals.md](brickadia-internals.md).

`BR` is a set of namespaces, one module each under `lua/omegga/brickadia/`:

| | |
|--|--|
| `BR.world` | game mode, grids, spawning actors, prefabs, raycasts |
| `BR.server` | server chat, console commands, the log, roles |
| `BR.brick` | placing and reading bricks, transactions, exec triggers |
| `BR.component`, `BR.wire`, `BR.var` | gates and components, wire values, variable gates |
| `BR.event` | player events, ticks, UFunction hooks, custom events |
| `BR.player`, `BR.team`, `BR.leaderboard` | players and what they see, teams, leaderboards |
| `BR.entity` | entities and dynamic grids |
| `BR.zone` | zones (zone projector bricks): their boxes and who is in them |
| `BR.npc` | the game's own AI bots (Bot Spawn bricks) |
| `BR.nav` | walking paths over a brick world |
| `BR.bot` | bots: players with no client behind them |
| `BR.act` | things a player does by hand (tools, chat, emotes, clicks), for bots and real players |
| `BR.voice` | audio through voice chat, as if a player said it |
| `BR.perm` | permissions: checking, per-player overrides of the game's, plugin-defined ones |
| `BR.store` | small JSON files saved with the world |
| `BR.timer` | delayed and repeating calls, optionally tied to an owner |
| `BR.command` | chat commands |
| `BR.mod` | kicking, bans, refusing players as they join |
| `BR.math` | vectors, quaternions, rotators and angles, in plain Lua |
| `BR.raw` | byte packing and raw UFunction calls |

## Editor completion

Completion works with [Lua Language Server](https://luals.github.io/) (the "Lua" extension in
VS Code, or `lua_ls` in Neovim). It draws on three sets of annotations:

| Where | What |
|--|--|
| `types/omegga.lua` in this plugin | `BR`, `Omegga`, the native helpers |
| `types/ue4ss.lua` in this plugin | UE4SS's own globals and base classes (`UObject`, `RegisterHook`, ...), as UE4SS ships them |
| `types/enums.lua` in this plugin | the game's names as aliases (`BR.BrickAsset`, `BR.Item`, ...), so string arguments complete; see [Names](#names) |
| `data/UE4SS/Mods/shared/types/` | every class, function, property and enum the game had loaded, generated by UE4SS |

The plugin generates the third set after the first map loads, and again only after the game binary
changes (it compares the binary against `.binary` in that folder). The output follows
whatever classes are loaded at the time, so delete `.binary` and restart to regenerate after
a map that loads more. `GenerateLuaTypes()` in any mod or `exec` regenerates it immediately.
Don't put your own files in that folder: the generator deletes every `.lua` file there first.

The first start also writes `data/Mods/.luarc.json`, which points the language server at all
three, so opening `data/Mods` in an editor just works. It is left alone once it exists. For a
mod shipped by an omegga plugin, give the plugin's `mods/` folder the same settings with the
paths for that server:

```json
{
  "runtime.version": "Lua 5.4",
  "workspace.library": ["<omegga>/plugins/ue4ss/types", "<omegga>/data/UE4SS/Mods/shared/types"],
  "workspace.preloadFileSize": 4096
}
```

`require` returns untyped values to the language server, so annotate the two modules:

```lua
---@type BRModule
local BR = require("omegga.brickadia")
---@type OmeggaModule
local Omegga = require("omegga")

local pc = FindFirstOf("BP_PlayerController_C") ---@cast pc ABP_PlayerController_C
```

### The watchdog

Every callback the bridge runs (ticks, timers, event handlers, hooks, delegate listeners,
bridge messages) has a time budget, 5 seconds by default. A callback that runs longer, such as
an endless loop in a handler, is stopped with a Lua error naming the file and line it was at
("...: the callback ran longer than 5000 ms and was stopped by the watchdog"), reported like any
other error, and the server carries on. `BR.server.watchdog(ms)` changes the budget (0 turns it
off) and returns the old one. The check runs every 10,000 Lua instructions, so it can't cut
short a single long call into the game. Tested: an endless loop in a timer was stopped at a
300 ms budget, and a timer due after it still ran.

## Names

Arguments that name something in the game (a brick asset, an item, an entity class, a rule
kind, an explosion, a permission, an emote, an emoji) take plain strings, and
`types/enums.lua` lists every one as a LuaLS alias, so an editor completes them:
`BR.brick.builder({ asset = "` offers the 527 brick assets. The file is generated from a
running server on Release-EA3-CL-16507; after a game update, regenerate it with
`npm run enums -- <bridge socket>`.

| | |
|--|--|
| `BR.enums.list(kind)` | the names of one kind, live from the game: `brick_asset`, `component`, `item`, `entity`, `explosion`, `team_rule`, `game_rule`, `permission`, `material`, `collision`, `emote`, `emoji` |
| `BR.enums.all()` | `{ [kind] = names }` (about 1.5 s: it walks every loaded object) |
| `BR.enums.render(build?)` / `BR.enums.write(path, build?)` | the alias file as text / written to `path` |

The lists come from what the game has loaded, which on a dedicated server is its whole
brick and item catalog.

## Errors

Lua errors land in `UE4SS.log` (in the server's `data/UE4SS/`), and the plugin repeats them in
omegga's own log, so a broken mod shows up where the server is being watched:

- **A `main.lua` that raises** leaves that mod not running. The server and the other mods carry
  on. Omegga logs `mod <name> failed to start and is not running:` with the error and traceback.
- **A callback a `BR` module runs** (an event handler, a tick, a timer, a command, a custom event
  listener, a hook, a join gate, ...) is caught, so the game and the other callbacks go on. It is
  logged as `[BR error] <where>: <error>`, `<where>` naming the API it came through
  (`BR.event.on chat`, `BR.timer`, `BR.command /heal`). A handler that errors counts as having
  returned nothing (it refuses nothing), and a repeating timer keeps repeating.
- **A callback UE4SS runs itself** (`RegisterHook`, `ExecuteInGameThread`) is caught by UE4SS,
  which logs `lua_pcall returned LUA_ERRRUN => <error>`.

The last two show in omegga's log as `mod <name> raised an error:`; the mod is named when the
error names a file under its folder. A broken tick handler fails every frame, so the same message
is shown once a minute at most, the next one saying how many times it came in between. Errors
already in `UE4SS.log` when the plugin starts are not repeated.

## Bricks

| | |
|--|--|
| `BR.brick.asset(name)` | a brick asset by name: `"PB_DefaultBrick"`, `"B_Bot_Spawn_Point"`, `"B_1x1_Gate_Expr_LogicalAND"` |
| `BR.brick.builder(opts)` | builder bytes. `opts`: `asset`, `size = {x, y, z}` (procedural bricks; half-extents in brick units), `color = {r, g, b, a}`, `material` (a `BR.brick.MATERIAL` name such as `"Glass"`, or its number; default `"Plastic"`), `alpha` (default 5), `grid`, `owner` (brick owner index), `visible = false`, `collision = false` |
| `BR.brick.MATERIAL` | `Plastic`, `Glass`, `TranslucentPlastic`, `Glow`, `Metal`, `Hologram` (`EBrickMaterial`) |
| `BR.brick.place(builder, x, y, z, orientation?)` | handle, or nil when refused. Immediate, no trust check, no undo. `orientation` defaults to `BR.brick.Z_UP` |
| `BR.brick.info(handle)` | `{ valid, asset, position = {x, y, z} }`, or `{ valid = false }` |
| `BR.brick.owner(handle)` / `BR.brick.owner_info(index)` | who owns a brick (or an owner index stands for): `{ index, id, name, display_name }` from the game's owner table, which keeps players who have left; index 0 is the shared "PUBLIC" owner |
| `BR.brick.valid(handle)` | whether the handle names a live brick |
| `BR.brick.id(handle)` | persistent id bytes, for transactions |
| `BR.brick.visible(handle)` | bool |
| `BR.brick.count(grid?)` | number of bricks |
| `BR.brick.COLLISION` | `EBrickCollisionChannels` bits: `Player`, `Player1`, `Player2`, `Player3`, `Weapon`, `Interaction`, `Physics`. A brick blocks what it has the bit for; `BR.brick.ALL_COLLISION` is all of them |
| `BR.brick.transform(t)` | FTransform bytes for entity transactions: `t = { pos = {x, y, z}, rot = {x, y, z, w}, scale = {x, y, z} or a number }` in world units; no rotation and scale 1 by default |
| `BR.world.load_prefab(name, x, y, z, orientation?)` | load a prefab bundle (`Saved/Prefabs/<name>.brz`) into the world, added to what's there; returns the number of bricks added. See below |

Brick helpers check the handle first and raise a Lua error for a dead one: the game's own
brick functions abort the server on an invalid handle.

Positions are integer brick units, and sizes are half-extents: `size = {10, 10, 6}` with `z = 6`
sits on the baseplate. Orientations: X+ 0..3, X- 4..7, Y+ 8..11, Y- 12..15,
Z+ 16..19, Z- 20..23.

### Loading many bricks at once

`BR.brick.place` costs about 70 ms for each fresh builder, so anything larger than a few hundred
bricks belongs in a prefab: write a `.brz` (brs-js `World` + `makePrefab()` + `toBrz()`, or the
brdb crate) into `Saved/Prefabs/` and load it with `BR.world.load_prefab`. Tested: 10,000 bricks load
in about 20 ms, inside the call, with their owners taken from the file.

- The prefab's bounds corner lands at `(x, y, z)` in world units.
- `orientation` defaults to `BR.brick.Z_UP` (16, Z+ with no rotation). The console
  command's own default, 0, is X+ facing and lays the whole prefab on its side.
- Bricks that would overlap existing ones are skipped; the game logs
  `Brick is overlapping in same grid (N)` under `LogBRWorldManager`.
- Compiled wirescript (`.brz`) loads the same way.

### Recipes

Tested:

```lua
-- a red brick
local h = BR.brick.place(BR.brick.builder({ asset = "PB_DefaultBrick", size = { 10, 10, 6 }, color = { 255, 0, 0, 255 } }), 0, 0, 6)

local L = "BRLuauBrickLibrary"
local lib = StaticFindObject("/Script/Brickadia.Default__BRLuauBrickLibrary")
local w = BR.raw.ptr(BR.world.context())

-- recolour (FColor bytes are B, G, R, A)
BR.raw.call(lib, L, "SetColor", { Self = h, NewColor = string.pack("BBBB", 0, 255, 0, 255), WorldContextObject = w })
-- move
BR.raw.bool(BR.raw.call(lib, L, "TryMove", { Self = h, NewPosition = BR.raw.ivec(0, 0, 30), WorldContextObject = w }).ReturnValue)
-- delete
BR.raw.call(lib, L, "DeleteBrick", { Self = h, WorldContextObject = w })

-- find a brick in a box
local grid = StaticFindObject("/Script/Brickadia.Default__BRLuauGridLibrary")
local r = BR.raw.call(grid, "BRLuauGridLibrary", "FindInBox", { Self = BR.raw.ptr(BR.world.global_grid()), Min = BR.raw.ivec(-10, -10, 0), Max = BR.raw.ivec(10, 10, 40) })
if BR.raw.bool(r.ReturnValue) then print(BR.brick.info(r.OutBrick).position[3]) end

-- every brick: a TArray of 8-byte handles {data, num, max}
local data, num = string.unpack("<I8i4", BR.raw.call(grid, "BRLuauGridLibrary", "GetBricks", { Self = BR.raw.ptr(BR.world.global_grid()) }).ReturnValue)
for i = 0, num - 1 do local handle = __peek(data + i * 8, 8) end
```

## Scripted bricks

`BR.behavior.define(name, spec)` gives every brick of some kind a behaviour, called for each
one: when it appears (there already, built, pasted, loaded, placed by Lua), when it is removed
by any route (a player, a wire, Lua, a reset), when a player presses it or a weapon hits it,
and on timers of its own. Each brick gets a `self` whose `state` it can save.

| `spec` field | |
|--|--|
| `assets` | asset names (`BR.BrickAsset`) it applies to |
| `match(handle, asset)` | instead of `assets`: `true` for bricks it applies to (read components, owner, position...) |
| `appear(self, how)` | `how` is `"existing"` (there when defined or when the world loaded) or `"placed"` |
| `remove(self)` | the brick is gone |
| `interact(self, player, info)` / `hit(self, player, info)` | a player pressed it / a melee or projectile hit it (`info` as for the player events) |
| `keep_state` | keep a removed brick's saved state (default: dropped) |

`self` is `{ brick, id, state, save(), every(seconds, fn), after(seconds, fn), forget() }`:
`state` is any JSON-able table, saved by `self:save()` (BR.store `behavior-<name>`, keyed by
the brick's id in the world) and back after a restart; `every`/`after` timers end with the
brick. `BR.behavior.bricks(name)` lists the selves, `BR.behavior.of(name, handle)` finds one,
and the function `define` returns removes the behaviour. Defining a name again replaces it.

```lua
BR.behavior.define("counter", {
    assets = { "B_1x1_Round" },
    appear = function(self) self.state.presses = self.state.presses or 0 end,
    interact = function(self, player)
        self.state.presses = self.state.presses + 1
        self:save()
        BR.player.whisper(player, "pressed " .. self.state.presses .. " times")
    end,
})
```

The game broadcasts no "brick removed", so the world grid is read every
`BR.behavior.interval` seconds (0.2 by default; about 3 ms for 4,600 bricks) and compared
with the last read, so `appear` and `remove` come up to that long after the change. The first
`define` reads every brick's asset once (about 190 ms for 4,600 bricks). Covers the world grid;
bricks on moving grids aren't included yet. Tested on Release-EA3-CL-16507: a brick placed by a
transaction got `appear "placed"`, and deleting it got `remove`.

## Components, gates and wires

| | |
|--|--|
| `BR.component.types()` | every registered component type object (about 400) |
| `BR.component.type(name)` | by transient name (`"BrickComponentType_Expr_LogicalAND"`) or part of a Blueprint type's name (`"BotSpawn"`, `"Component_BrickPropertyChanger"`) |
| `BR.component.ports(type)` | `{ inputs = {...}, outputs = {...} }`: the port FNames refs use |
| `BR.component.input_port(type, port)` / `BR.component.output_port(type, port)` | port ref bytes |
| `BR.component.port_name(port)` | a port ref's name back |
| `BR.component.handle(handle, type)` | the brick's component of that type as its 8-byte component handle (the id wires address), or nil |
| `BR.wire.bool(v)`, `BR.wire.int(v)`, `BR.wire.double(v)`, `BR.wire.string(text)` | wire value bytes |
| `BR.player.server()` | the PlayerState Lua acts as: transactions, admin gates, its own bricks ([why](brickadia-internals.md#transactions-and-trust)). Not in `BR.player.list()` |
| `BR.player.owner_index()` | that player's brick owner index; place bricks you'll edit with `owner = BR.player.owner_index()` |
| `BR.brick.transaction(player, fn)` | run `fn(tx)` to record actions, execute, return the report counters and `lines` (messages such as admin gate refusals) |
| `BR.brick.changes(report)` | only the non-zero counters, and `lines` if any |
| `BR.component.set_input(handle, type, port, value)` | one-action transaction; returns the report |
| `BR.component.input_is(handle, type, port, value)` | read an input back: true if it already holds `value`. If not, it now does |

A transaction runs once, after `fn` returns, with the player's trust and quotas checked the way
the game checks that player's own building. `tx` records actions in order. Bricks are named by id
(`BR.brick.id`, or the id `tx.place` returned, as bytes or a number); entities by the actor or its
id. Positions and sizes are whole grid units, orientations as for `BR.brick.place` (default
`BR.brick.Z_UP`).

| Action | |
|--|--|
| `tx.place(builder, {x, y, z}, orientation?, grid?)` | returns the new brick's id, usable later in the same transaction. `grid` is a dynamic grid entity; the world grid by default |
| `tx.restore(id, builder, {x, y, z}, orientation?, grid?)` | put a deleted brick back under its old id |
| `tx.delete(id)` | |
| `tx.move(id, {x, y, z}, orientation?)` / `tx.reorient(id, orientation)` | |
| `tx.resize(id, size, {x, y, z})` | procedural bricks; `size` is half extents |
| `tx.color(id, {r, g, b, a?}, material?, alpha?)` | With a material, the material and alpha (default 5) change too; alpha needs a material |
| `tx.material(id, material, alpha?)` | a `BR.brick.MATERIAL` name or number; `alpha` defaults to 5 |
| `tx.collision(id, channels)` | `BR.brick.COLLISION` bits, or `true` / `false` for all or none |
| `tx.visible(id, visible)` / `tx.owner(id, ps)` | |
| `tx.set(id, inputPort, wireValue)` | a component input |
| `tx.connect(srcId, outputPort, dstId, inputPort)` / `tx.disconnect(...)` | a wire, same arguments |
| `tx.attach(id, componentType)` / `tx.detach(id, componentType)` | a component type object (`BR.component.type`) |
| `tx.place_entity(class, transform, opts?)` | returns the new entity's id; `opts.frozen`, `opts.owner` (owner index) |
| `tx.move_entity(entity, transform)` / `tx.delete_entity(entity)` | |
| `tx.entity_color(entity, slot, {r, g, b, a?})` | |
| `tx.physics(entity, enabled)` | |
| `tx.connect_joint(jointId, entity, transform)` / `tx.disconnect_joint(jointId, entity)` | connect an entity to the joint `jointId` (an id) at `transform`, or disconnect it |

A transform is a `BR.brick.transform` table or its bytes. Report counters: `BricksPlaced`,
`BricksUntrusted`, `ComponentsChanged`, `ComponentsSkipped`, `ComponentsAttached`,
`WiresConnected`, `EntitiesPlaced`, ... (all 34 in `TransactionReport`, `types/omegga.lua`).

Tested on Release-EA3-CL-16507: place, move, resize, color (with and without a material),
material, collision, visible and delete, by the acceptance run. Placing many bricks in one
transaction is fast: 100 bricks took 2.7 ms, against about 70 ms per brick for
`BR.brick.place`. A brick that would overlap another is counted in `BricksBlocked` and not
placed, and later actions on its id count as `BricksNotFound`. `BR.player.server()` is
allowed every game permission, so transactions run as it are refused only for trust or quotas.
Placing an `Entity_Ball`, moving it, colouring it, switching its physics and deleting it were
tried by hand; the joint actions are not yet tried.

Port names are the component's property names, not display names: LogicalAND has `bInputA`,
`bInputB` -> `bOutput`; MathAdd `InputA`, `InputB` -> `Output`. Use `BR.component.ports` to find them. Use
the port's own kind: numbers are doubles (`wire_double`); an integer written to a double input
counts as a different value.

### Recipes

Tested; setting and reading a gate input is also in the acceptance run.

```lua
local AND, ADD = "BrickComponentType_Expr_LogicalAND", "BrickComponentType_Expr_MathAdd"
local ps, owner = BR.player.server(), BR.player.owner_index()

-- two AND gates, the first feeding the second
local a = BR.brick.place(BR.brick.builder({ asset = "B_1x1_Gate_Expr_LogicalAND", owner = owner }), 0, 0, 6)
local b = BR.brick.place(BR.brick.builder({ asset = "B_1x1_Gate_Expr_LogicalAND", owner = owner }), 40, 0, 6)
BR.brick.transaction(ps, function(tx)
    tx.connect(BR.brick.id(a), BR.component.output_port(AND, "bOutput"), BR.brick.id(b), BR.component.input_port(AND, "bInputA"))
    tx.set(BR.brick.id(a), BR.component.input_port(AND, "bInputA"), BR.wire.bool(true))
    tx.set(BR.brick.id(a), BR.component.input_port(AND, "bInputB"), BR.wire.bool(true))
end)  -- { WiresConnected = 1, ComponentsChanged = 2, ... }

-- a number
local add = BR.brick.place(BR.brick.builder({ asset = "B_1x1_Gate_Expr_MathAdd", owner = owner }), 80, 0, 6)
BR.component.set_input(add, ADD, "InputA", BR.wire.double(5))
assert(BR.component.input_is(add, ADD, "InputA", BR.wire.double(5)))

-- give a plain brick a component
local brick = BR.brick.place(BR.brick.builder({ asset = "PB_DefaultBrick", size = { 5, 5, 6 }, owner = owner }), 120, 0, 6)
BR.brick.transaction(ps, function(tx) tx.attach(BR.brick.id(brick), BR.component.type("Component_BrickPropertyChanger")) end)
```

`BR.component.input_is` reads through the transaction report: re-setting the current value is
*skipped*, any other value is *changed* (and applied). It raises an error for any other result.
It can't read **wired** inputs: a Set on a wired input is always skipped, which would look like
"already that value". To observe outputs, see [signal bricks](interop.md#reacting-to-component-changes).

### Firing exec gates

| | |
|--|--|
| `BR.brick.trigger(x, y, z)` | place a trigger gate; returns `t` with `t.brick`, `t.connect(target, type, port)`, `t.fire()` |

Every `t.fire()` fires whatever its wire leads to, one tick later. Wire it to any exec input:
Broadcast Chat Message, a Send Custom Event brick, a branch. Connect, then fire from a later
call: a wire isn't live in the tick it was made. Tested on Release-EA3-CL-16507 (one chat line per fire):

```lua
local CHAT = BR.component.type("Gamemode_BroadcastChatMessage"):GetFName():ToString()
local chat = BR.brick.place(BR.brick.builder({ asset = "B_1x1_Gate_Exec_Gamemode_BroadcastChatMessage", owner = BR.player.owner_index() }), 40, 0, 6)
_G.T = BR.brick.trigger(0, 0, 6)
_G.T.connect(chat, CHAT, "Exec")
-- later
_G.T.fire()
```

## Component data

Every component's settings, not only its wire inputs: bot spawner tuning, custom event names,
button labels. Written with the engine's own property changelists
([format](brickadia-internals.md#property-changelists)).

| | |
|--|--|
| `BR.component.set(handle, type, values)` | set fields; `values` maps field paths to Lua values |
| `BR.component.get(handle, type, path)` | read one field (`"GunSkill"`, `"MoveTarget.X"`) |
| `BR.component.data(handle, type)` | every readable field as a table, or nil if the brick has no such component |
| `BR.component.fields(type)` | `{ { name, type } }` for every field, inherited ones included (Interact's `PromptCustomLabel` comes from its base) |
| `BR.component.struct(type)` | the component's data struct (a UScriptStruct) |
| `BR.component.address(handle, type)` | where the data lives, for reading it raw |
| `BR.wire.read(address)` | the wire value at an address, decoded as reads are below |

```lua
local spawn = BR.brick.place(BR.brick.builder({ asset = "B_Bot_Spawn_Point", owner = BR.player.owner_index() }), 0, 80, 6)
BR.component.set(spawn, "BotSpawn", {
    GunSkill = 0.25,
    bActiveBot = false,
    BotName = "Lua Bot",
    ["MoveTarget.X"] = 100,          -- a field inside a struct field
})
```

Each value is converted to the field's own type, read from reflection:

| Field type | Lua value |
|------------|-----------|
| `BoolProperty` | boolean |
| `Int8Property` ... `UInt64Property`, `ByteProperty` | integer |
| `FloatProperty`, `DoubleProperty` | number |
| `Struct<WireString>` (names, labels, messages) | string |
| a struct (`Struct<Vector>`, ...) | write its fields with a dotted path |

Anything else (arrays, maps, enums, object references) raises an error naming the field and
its type, as does an unknown field. The write applies at once, without a transaction or trust
check (like `BR.brick.place`), and works on a brick's built-in components as well as attached ones.
A mismatch the engine itself refuses is logged under `LogBRPropertyChange` and leaves the
field unchanged. Tested on Release-EA3-CL-16507: bool, uint8, float and WireString fields, several fields at
once, on built-in and attached components.

Reads return booleans, numbers, strings for `WireString` fields, wire values (decoded:
booleans, numbers, strings, `{x, y, z}` vectors; `{ kind = n }` for kinds not decoded yet) and
nested structs as tables; object references and containers read as nil. They are plain memory
reads, cheap enough to run every tick:

```lua
local d = BR.component.data(spawn, "BotSpawn")
print(d.GunSkill, d.BotName, d.MoveTarget.X)
print(BR.component.get(gate, "BrickComponentType_Expr_LogicalAND", "bOutput"))   -- a gate's output
```

### Array and map variables

Array Variable and Map Variable gates hold their contents in structs with no reflected fields,
so these read and write the memory directly
([layouts](brickadia-internals.md#array-and-map-variables)). The element type is fixed by the
gate, or by the circuit that declared the variable, and values are converted to it.

| | |
|--|--|
| `BR.var.read_array(handle)` | the elements as a list, and the element type's name |
| `BR.var.write_array(handle, values)` | replace the elements |
| `BR.var.read_map(handle)` | the entries as `{ { key, value }, ... }`, and the key and value type names |
| `BR.var.set_map_value(handle, key, value)` | change the value of an existing key; false if the key isn't there |
| `BR.brick.in_grid(grid?)` | every brick on a grid, to find gates inside a microchip |
| `BR.brick.in_sphere(center, radius, opts?)` | bricks within `radius` of `center`, in the grid's space (world space on the global grid); `opts.grid`, `opts.max` (default 10000) |
| `BR.brick.in_box(min, max, opts?)` | bricks touching a box given in whole grid units |
| `BR.var.on_change(target, fn)` | `fn(value, handle)` when a Variable gate's value changes |
| `BR.var.on_array_change(target, fn)` | `fn(elements, handle)` when an Array Variable gate changes |
| `BR.var.on_map_change(target, fn)` | `fn(entries, handle)` when a Map Variable gate changes |

Element types so far: `int` (Int64), `float` (Double) and `string` (WireString), for arrays and
for map keys and values. Others raise an error naming the type.

```lua
-- a circuit's arrays, from its microchip grid
local chip = FindAllOf("BP_MicrochipBrickGridDynamicActor_C")[1]
for _, h in ipairs(BR.brick.in_grid(chip)) do
    if BR.component.address(h, "BrickComponentType_ArrayVar") then
        local values, kind = BR.var.read_array(h)
        if kind == "BRReflectionPropertyInfo_WireString" then
            BR.var.write_array(h, { "alpha", "beta", "gamma" })
        end
    end
end
```

`target` for the change events is a gate's handle, a list of handles, or a grid (every such gate
on it at the time of the call, so a microchip's grid covers a whole circuit). Each returns a
function that stops watching, and how many gates it watches. The game changes these values in
native wire code that no hook sees, so each gate is checked once a tick (arrays and maps by a
change counter, variables by their value bytes): changes within one tick arrive as one call
with the latest contents, and Lua's own writes fire too.

```lua
local chip = FindAllOf("BP_MicrochipBrickGridDynamicActor_C")[1]
local stop = BR.var.on_array_change(chip, function(elements, handle)
    print(#elements, "elements in", BR.brick.id(handle))
end)
```

Gates read the new contents on their next run, and array gates keep working on them (a Push
after `write_array` grows the array normally). Gates that react only to changes made through
other array gates are not told. Map keys can't be added or removed here, because lookups go
through a hash index; add keys with a Set gate. Replaced strings are not released, which leaks a
few bytes each.

## Custom events

Send Custom Event gates reach the receivers whose event name matches. Global events reach
every matching receiver in the world; targeted events reach only receivers on the target
entity (a brick grid: a contraption, vehicle or other dynamic grid).

| | |
|--|--|
| `BR.event.custom(name, opts?)` | returns `ev`, whose `ev.send(...)` sends the event `name` |
| `BR.event.on_custom(name, fn, opts?)` | `fn(data, info)` for every event named `name`; returns a function that stops it |
| `BR.event.on_any_custom(fn)` | `fn(data, info)` for every custom event, any name, global or targeted |
| `BR.world.grids()` | every dynamic brick grid entity |
| `BR.brick.grid(handle)` | the grid a brick is on (the global grid or an entity) |

| Option | `custom` | `on_custom` |
|--------|----------|-------------|
| `target = grid` | send only to that entity | |
| `owner = n` | with `target`: reach receivers built by owner index `n` (default the entity's owner) | |
| `entity = grid` | | listen for events sent to that entity |

BR works with the game's own custom event routing, so neither side needs gates per event:

- **Sending** is immediate, from any call, including the one that made `ev`. `ev.send(...)`
  takes up to 8 wire values for `DataIn1..8` (`BR.wire.bool / int / double / string`); missing
  ones are 0, as on an unconnected input. Every send counts, but an in-game receiver plays one
  event per tick from a queue that holds 64, so a larger burst is cut short for that gate.
- **Listening** hears every sender, in-game gates included, once per event, at the start of the
  next tick. `data` holds the 8 values as Lua values (booleans, numbers, strings, vectors).
  `info` is `{ name, target, sender }`: `target` is the id of the entity a targeted event went
  to (0 for a global one), and `sender` the sending gate's component handle. Without `entity`,
  `on_custom` hears global events only, like a global receiver gate.
- **Targeted events** go to receivers on that entity that listen for object events. The game
  routes one to receivers built by the sender's owner, so BR sends as the entity's owner, or as
  `owner` (an owner index) when given. `ev.send` returns how many receiver gates it reached.
  Lua listeners hear every send whoever owns the receivers.

```lua
-- global
BR.event.on_custom("door_open", function(data, info)
    Omegga.emit("door_open", { by = data[1] })
end)
BR.event.custom("door_open").send(BR.wire.string("lever 3"))

-- one vehicle
local car = BR.brick.grid(some_brick_on_the_car)
BR.event.on_custom("honk", function() print("honk") end, { entity = car })
BR.event.custom("honk", { target = car }).send()

-- everything, for debugging a build's circuits
BR.event.on_any_custom(function(data, info) print(info.name, info.target, data[1]) end)
```

Tested on Release-EA3-CL-16507: three sends in one call reached a listener in order and a
listener for another name stayed quiet; an in-game receiver gate counted three sends from BR,
and a listener heard an in-game sender fired by a trigger; a targeted send reached the
listener on its grid once, while the same name on a second grid and a global listener stayed
quiet, and a receiver gate on the target grid counted it.

How it works: every Send Custom Event gate ends in one native dispatcher, which the bridge
hooks to hear events. To send, BR looks the event up in the registry the dispatcher uses
(receivers by name, global or per owner, then by target entity) and queues it on each receiver
with the same functions the dispatcher calls, so no gate is placed.

Existing senders and receivers built in game can be renamed with
`BR.component.set(brick, "Event_CustomGlobal", { EventName = "door_open" })`. A receiver's
event list in game only offers names some Send Custom Event gate in the world uses, and BR
sends without one, so a name only BR sends has to be set on the receiver this way (or a
sender gate with that name placed somewhere). Seen on Release-EA3-CL-16507: once named, a
player's receivers got BR's sends.

## Player events

| | |
|--|--|
| `BR.event.on(event, fn)` | `fn(player, info)` when a player does `event`; returns a function that stops it |
| `BR.event.EVENTS` | the event names |
| `BR.player.of(obj)` | the PlayerState behind a controller, character, tool or weapon, or nil |
| `BR.event.tick(fn)` | `fn(deltaSeconds)` at the start of every engine tick; returns a stop function |

`player` is the PlayerState (bots included). Handlers run on the game thread *before* the
game handles the action, so a brick about to be deleted can still be read.

Events marked "can refuse" are a player's request to the server. A handler returning `false`
refuses it: the server acts as if the request never came. A `chat` handler can instead return a
string, which goes out in place of the message (any text, emoji included). Every handler still
sees the event, whichever refuses. The player's own client may have shown the action already
(its new avatar, a brick preview) until the server's state corrects it.

```lua
-- no building near spawn, and a word filter
BR.event.on("place", function(player, info)
    if info.position and math.abs(info.position[1]) < 2000 and math.abs(info.position[2]) < 2000 then
        BR.player.whisper(player, "No building at spawn")
        return false
    end
end)
BR.event.on("chat", function(player, info)
    return (info.message:gsub("[Hh]eck", "h*ck"))
end)
```

each, and a new world's game mode gets the bindings within a second. `player` is nil for the

live server or for a spawned stand-in character (a chat message, a death, a button press). The untested ones hook
the RPC a real client sends; the payload offsets come from reflection, but they haven't seen a
real call yet. Reload and voice have no server-side RPC (weapon state replicates as a
property, and voice doesn't pass through UFunctions on the server), so they aren't events.

`BR.event.hook` and `BR.event.after` see calls that go through ProcessEvent, which includes every RPC a
client sends and every Blueprint event, but not native C++ calling C++. A call a `hook` stopped
never reaches `after` (tested: a bot's chat line ran `after` once, a blocked one didn't).
Replacing a return value works for whoever made the call through ProcessEvent: Lua, Blueprints,
and native code calling a Blueprint event (tested: `GetPingInMilliseconds` called from Lua returned
the replaced value).

```lua
local path = "/Script/Engine.PlayerState:GetPingInMilliseconds"

```

`projectile_hit` reports the player who fired (`InstigatorState`). The hit result names the struck

A pistol that builds where it hits, in the shooter's paint (see [Players and teams](#players-and-teams)
for the paint selection):

```lua
BR.event.on("projectile_hit", function(player, info)
    if not player or info.character then return end

    local x = math.floor((p[1] + n[1] * 5) / 10) * 10 + 5
    local y = math.floor((p[2] + n[2] * 5) / 10) * 10 + 5
    local z = math.floor((p[3] + n[3] * 6 - 6) / 4 + 0.5) * 4 + 6
    local owner = FindFirstOf("BRGameStateBase"):IdOrRegisterBrickOwner(BR.player.controller(player))
    BR.brick.place(BR.brick.builder({ size = { 5, 5, 6 }, owner = owner }), x, y, z)

```

```lua
ch.CharacterScale = 2.0
```

### Team rules

The game mode editor's team rules are objects (`BRGameModeTeamRule_<Kind>`) whose setters take
effect at once and replicate, so a real client moves with the same values the server uses.
They are the safe way to change a group's movement and abilities, rather than editing
movement fields only the server sees. Some kinds: `EnhancedBrickadians` (walk, sprint, fly
speed, jump height, health, grab force multipliers), `HealthRegeneration`, `InfiniteAmmo`,
`KeepInventory`, `WaterDamage`, `RestrictedChatRange`, `RestrictedVoiceChat`, `RestrictedItems`,
`RestrictedBricks`, `CustomCollision`, `Uniform`, `Music`, `HiddenTeam`, `TrackScore`. Rules added
here last until the game mode is reset or reloaded; its saved settings don't change.

Rules exist only on teams and on the game as a whole: players and characters have no rule
container. For one player, put them on a team of their own (`BR.team.create`); for everyone,
add the kind as a game-wide rule (`BR.world.rule`). Both were checked on a bot: a team's
`SetWalkSpeedMultiplier(2)` doubled its max speed (148 to 296), and the same rule game-wide
applied to a player with no team (148 to 222 at 1.5) and was undone by removing it.

```lua
local slow = BR.team.create("Prisoners", { color = { 120, 120, 120 }, friendly_damage = false })
local rule = BR.team.rule(slow, "EnhancedBrickadians")
rule:SetWalkSpeedMultiplier(0.5)
rule:SetAllowSprintWalking(false)
BR.team.join(ps, BR.team.info(slow).id, false)
```

## Status effects

`BR.effect` applies timed effects to a player's character. They stack by their own rule, can
tick, and end when their time runs out, when removed, or with the character (death, respawn,
leaving).

| | |
|--|--|
| `BR.effect.apply(ps, name, opts?)` | `opts`: `duration` (seconds; nil until removed), `strength` (the effect's measure, default 1), `stacks`; returns its `self` |
| `BR.effect.remove(ps, name?)` | end one effect, or all |
| `BR.effect.of(ps)` | `{ [name] = self }` |
| `BR.effect.define(name, spec)` | a new effect: `apply(self)`, `tick(self, seconds)` every `interval` (default 1), `remove(self)`, `restack(self)`, `stack` (`"refresh"`, `"add"`, `"max"`), `max_stacks` |

Built in: `regen` and `poison` (`strength` health per second, times stacks; poison stacks by
adding), and `size` (`strength` is the character scale, restored when it ends). `self` is
`{ name, player, character, stacks, strength, expires, data }`.

Effects change what the server decides (health, replicated character state). Movement speed and
jump height are predicted by the client, so effects on them belong in team rules
(`BR.team.rule`), where the client gets the same values. Tested on a bot: poison stacked to 2,
size went to 2 and back to 1 when it ended, and regen healed back to full. A game mode's own
health regeneration rule keeps healing alongside poison.

## Movement

| | |
|--|--|
| `BR.player.movement(ch)` | `{ seated, sitting, crouching, sprinting, walking, moving, speed, mode, in_water }` |
| `BR.player.sitting(ch)` / `crouching` / `sprinting` / `walking` | one of those fields |
| `BR.player.in_water(ch)` | in the world's water or a water zone |
| `BR.player.in_zone(ch, zone)` | in a zone ([Zones](#zones)) |
| `BR.event.on_sprint(fn)` / `on_walk` / `on_crouch` / `on_sit` / `on_water` | `fn(player, active, character)` when a player starts (`active` true) or stops; returns a stop function |
| `BR.event.on_zone(zone, fn)` | `fn(player, active, character)` when a player enters or leaves `zone` |
| `BR.player.input(ch)` | what the player is pressing, as the server last heard: `{ keys = { primary, secondary, reload, inspect, custom1..custom4 = true }, move = {x, y, z} }` (`move`: the world direction their movement input pushes) |
| `BR.event.on("key", fn)` | `fn(player, { key, down, character })` when a player presses (`down`) or releases a weapon key; `BR.event.KEYS` names them |

Keys are the weapon keys a client sends with each move (fire, aim, reload, inspect and the four
custom weapon binds), so they arrive while the player holds something that takes input; the
`key` event is polled with the movement states. Tested on a bot firing a pistol: `primary` down
and up, and `move` pointing where it walked.

The states don't overlap: `sitting` (in a seat brick, or the Sit emote) rules out the rest,
`crouching` rules out sprinting and walking, and `walking` is moving on the ground without
sprinting. `sprinting` is the game's own sprint state while the character moves, on the ground
or flying; `speed` is horizontal, in units per second, and `mode` is `walk` (on the ground),
`fall`, `fly`, `swim`, `none` or `custom`.

Crouch and sprint arrive as flags on every client move, and walking is only velocity, so nothing
can be hooked: these events come from checking every character 10 times a second, and fire up
to 0.1 s late. A character dying or its player leaving ends its states (`active` false, no
`character`). A state a character already has when it is first seen (a player who joins
seated, or after a `BR_RELOAD`) is reported as a start.

With tap-to-sprint, which a server's default controls settings have on, the game keeps a sprint
going after the key is let go until the character slows down or turns back, and `sprinting`
follows the game. `BR.bot.sprint(ps, false)` ends a bot's sprint at once.

```lua
BR.event.on_crouch(function(player, active)
```

### Screen elements and transitions

`BR.ui` builds on the same call with elements that remember their state, so a change is one
call and can animate: the game's display text takes a `Transition` (seconds) and `Easing`,
and the client moves, scales, rotates and recolours an element from what it showed to what it
is sent. No gate is involved. Elements shown to `"all"` are also sent to players who join
later. **Not yet seen on a real client**; `/uidemo` on a test server is the quickest look.

| | |
|--|--|
| `BR.ui.text(target, opts)` | text; `target` is a PlayerState, a list of them, or `"all"`. Returns an element |
| `BR.ui.panel(target, opts)` | a solid rectangle `opts.w` by `opts.h` (screen units) in `opts.color`, with the same placement options |
| `el:set(changes, { transition?, easing? })` | change options and resend; with a transition the client animates to the new state |
| `el:move(x, y, seconds?, easing?)` / `el:remove()` | |
| `BR.ui.remove(target, id)` | remove by id |
| `BR.ui.ask(ps, opts, fn)` | a dialog box with an answer: OK, Yes/No, OK/Cancel or text input (below) |
| `BR.ui.ANCHOR` / `EASING` / `ALIGN` / `TYPEFACE` | the names the options take |

Options: `text` (rich text: `<b>`, `<color="ff8800">...</>`), `x`, `y` (screen units at 1080p
from the anchor), `anchor` (`top_left`, `top`, `top_right`, `left`, `center`, `right`,
`bottom_left`, `bottom`, `bottom_right`, or `{x, y}` fractions), `pivot` (defaults to the
anchor, so a `bottom_right` element grows up and left from its point), `size` (font size),
`color` (`{r, g, b, a}` or `"rrggbb[aa]"`; fade by animating alpha), `outline`,
`outline_color`, `shadow` (`{x, y}`), `shadow_color`, `scale`, `angle`, `z`, `wrap`, `align`,
`font` (a `BR.Font`: `Bungee`, `Orbitron`, `RobotoMono`, ...), `typeface` (`bold`, `italic`,
`bold_italic`), `spacing`, `skew`, `line_height`, `lifetime` (seconds), `transition` and
`easing` for the first send, `id` (a fixed id). Easings: `linear`, `ease_in`, `ease_out`,
`ease_in_out`.

Who put a text on a player's screen: `BR.ui.texts(ps, { sources = true })` lists what their
client holds, oldest first, each `{ id, expires, from }` (`from` is `"BR.ui"` or `"world"`), and
a world text's `sources`, the Display Text gates that send that id with each brick's owner.
`BR.ui.sources(id)` does the lookup for one id. Finding the gates means checking every brick
(about 90 ms for 5,000), so the list is kept for 30 seconds (`{ refresh = true }` rescans), and
nothing scans on its own: only these calls do.

A client holds at most 32 display texts (`BR.ui.LIMIT`): one with a new id when it already has
32 makes it drop the oldest, without a word. The number is compiled into the game client, so
the server can't raise it; updating an element doesn't count, only new ids do, and texts from
the world's Display Text gates share the 32. `BR.ui.count(ps)` says how many a player's client
holds (BR.ui's and the gates', counted since the module loaded), and when one gets dropped,
omegga's console says so (at most every 10 seconds). To fit more on screen:

- Put lines that move together in one element: a scoreboard or a list is one `text` with
  newlines, each line styled with rich text (`<color>`, `<size>`, `<b>`).
- Reuse an element with `el:set` rather than removing it and making a new one.
- Give passing messages a `lifetime`, so the client lets them go by itself.

`BR.ui.ask(ps, opts, fn)` asks a connected player with the game's dialog box (the one the
Message Box gate shows) and calls `fn(accepted, text)` with the answer: `accepted` is true for
OK/Yes and false for Cancel/No, and `text` is what they typed in a `"text"` dialog. If it
couldn't open, or `opts.timeout` seconds pass first, `fn(nil, "failed")` or `fn(nil, "timeout")`.
The game can't close a dialog from the server, so a timed-out one stays on the player's screen
until they answer it, and that late answer is dropped.
`opts`: `title`, `message`, `kind` (`"ok"`, `"yes_no"`, `"ok_cancel"`, `"text"`), `timeout`,
`from` (the owner index it names as the source). Answers to BR's dialogs are taken out before
the game sees them, so gates' own dialogs are unaffected. Seen on a real client on
Release-EA3-CL-16507: each kind answered as expected, and a timeout fired while its dialog
stayed open.

```lua
BR.ui.ask(ps, { title = "Join the arena?", kind = "yes_no", timeout = 30 }, function(yes)
    if yes then BR.team.join(ps, arena_id, true) end
end)
```

```lua
local bar = BR.ui.panel("all", { anchor = "top", y = 40, w = 0, h = 8, color = "d97757" })
bar:set({ w = 600 }, { transition = 10 })                     -- a 10 s progress bar
local msg = BR.ui.text("all", { anchor = "center", text = "<b>GO</>", size = 64, scale = 0.2 })
msg:set({ scale = 1.5 }, { transition = 0.4, easing = "ease_out" })
BR.timer.after(2, function() msg:set({ color = { 255, 255, 255, 0 } }, { transition = 0.5 }) end)
```

## Inventory, templates and prefabs

A player's hotbar slots and their template (the slot the placer builds from, which picking a
brick from the catalog or copying a selection fills) can hold a brick, an entity, a prefab or an
item. `BR.prefab` puts things there with the same server calls the client makes, so the game
checks the player may hold them.

| | |
|--|--|
| `BR.prefab.set_slot(ps, slot, what)` | put `what` in hotbar slot `slot` (0-based) |
| `BR.prefab.set_template(ps, what)` / `BR.prefab.clear_template(ps)` | put `what` on the template / empty it |
| `BR.prefab.copy(ps, center, size, grid?)` | copy the bricks in a box (grid units; `size` is the full size) onto a connected player's template, as their selector's copy does |
| `BR.prefab.save(path, center, extent, { entities? })` | save a box (`extent` is half the size) to `Saved/Prefabs/<path>.brz` (`br.Prefab.SaveRegion`) |
| `BR.prefab.give(ps, path, preserve_ownership?)` | put the prefab file `<path>` on a connected player's template (`br.Prefab.GiveToPlayer`) |
| `BR.prefab.cached()` | the prefabs the server has cached: `{ hash, bricks, entities, components, wires, size }` |
| `BR.prefab.template(what)` | the template bytes, for raw calls |

`what` is one of `{ brick = "B_1x1_Round" }` (a `BR.BrickAsset`; `size = {x, y, z}` half extents
for procedural bricks, default the asset's own), `{ entity = "Entity_Ball" }`, `{ prefab = hash }`
(64 hex digits, from `BR.prefab.cached`; `preserve_ownership`), `{ item = "Weapon_Pistol" }`, with
`count`.

```lua
BR.prefab.set_slot(ps, 8, { brick = "B_1x1_Round" })
BR.prefab.set_template(ps, { brick = "PB_DefaultBrick", size = { 10, 10, 2 } })
BR.prefab.save("arena/spawn", { 0, 0, 100 }, { 200, 200, 100 })
BR.prefab.give(ps, "arena/spawn")
```

Tested on bots on Release-EA3-CL-16507: bricks (fixed and procedural), entities, items and cached
prefabs into slots and onto the template; `copy`, `save` and the file and cache steps on the
server. Not yet seen on a real client. `give` needs a connected player (the game finds the
player by id, and bots all share an empty one); for a bot, `set_template` with the cached hash
does the same. The game's inventory calls act on the controller's pawn and do nothing
without one; a bot's character belongs to an AI controller, so `BR.prefab` points the bot's
player controller at it for the length of the call.

## Suspicious play

`BR.guard.on(kind, fn, opts?)` calls `fn(player, amount, info)` on a signal of suspicious play.
It only detects: what to do (log, warn, kick, freeze) is the mod's call. Bots are left out
unless `opts.bots`. Returns a function that stops it.

| Kind | Fires when | `amount` | `info` |
| --- | --- | --- | --- |
| `speed` | faster on the ground than the character's own top speed (which follows sprinting, crouching and team rules) times `opts.tolerance` (1.25), for `opts.sustain` polls in a row (3, so 0.3 s) | speed over top speed | `character`, `speed`, `max` |
| `teleport` | moved further between two polls than its velocity explains, plus `opts.slack` units (300) | distance | `character`, `from`, `to` |
| `fly` | flying for 0.2 s without `BR.Permission.Fly` | 1 | `character` |
| `build_rate` | more than `opts.max` (20) place requests in a second; a request can place many bricks | requests in the last second | |

Movement is sampled 10 times a second from what the server simulates. The server already
corrects moves it finds impossible, so these mostly catch what gets through its tolerance, and
settings that disagree with the client. Moves made with `BR.world.teleport` and new characters
don't count as teleports; the game's own (teleporter bricks, admin teleports) do, so check
where a player went. A mod moving characters some other way can call
`BR.guard.expect_move(character)` first.

```lua
BR.guard.on("fly", function(ps)
    BR.mod.kick(ps, "flying without permission")
end)
```

Tested with bots on Release-EA3-CL-16507: `teleport`, `fly` and `build_rate`. `speed` hasn't been
provoked in a test: the server holds a bot's character to its top speed.

## Procedural generation

`BR.gen` has the pieces for generated maps: a seeded random number generator, noise, a check
for free space, and generators that build in one transaction. Worlds are saved whole, so
generation runs when a mod decides (a round start, a command), not as chunks load.

| | |
|--|--|
| `BR.gen.rng(seed)` | a generator from a number or string seed; the same seed gives the same numbers on every server (unlike `math.random`). `rng:next()` (32-bit integer), `rng:float()` ([0, 1)), `rng:int(a, b)`, `rng:chance(p)`, `rng:pick(list)`, `rng:shuffle(list)` |
| `BR.gen.noise(seed)` | `noise(x, y, z?)`: smooth Perlin noise in about [-1, 1], changing over a distance of about 1 (scale the inputs) |
| `BR.gen.fbm(noise, x, y, z?, opts?)` | layered noise: `octaves` (4), `lacunarity` (2), `gain` (0.5) |
| `BR.gen.fits(min, max, opts?)` | whether a box (whole grid units) has no bricks |
| `BR.gen.scatter(rng, min, max, count, opts?)` | up to `count` points `{x, y}` in a rectangle, `opts.spacing` apart |
| `BR.gen.terrain(origin, {w, h}, opts?)` | noise terrain of `w` by `h` columns from the corner `origin`: `cell` (half width, 10), `layers` (tallest, 8), `layer` (half height, 2), `scale` (cells per feature, 12), `seed`, `octaves`, `colors = { low, high }` |
| `BR.gen.maze_grid({w, h}, rng)` | a maze as a (2w+1) by (2h+1) grid of booleans, true for wall; every cell reachable by exactly one path |
| `BR.gen.maze(origin, {w, h}, opts?)` | build one: `block` (half width, 10), `height` (half height, 30), `color`, `seed`; each row's wall runs are single bricks. Returns the report and the grid |

The builders take `player` (whose transaction; the server stand-in by default), `material` and
`owner` too, and return the transaction's report. On Release-EA3-CL-16507 a 16 by 16 terrain (256
columns) builds in 18 ms and an 8 by 8 maze (90 bricks) in 3 ms.

```lua
local rng = BR.gen.rng("round " .. round)
local area = { x, y, 0 }
if BR.gen.fits(area, { x + 320, y + 320, 100 }) then
    BR.gen.terrain(area, { 16, 16 }, { seed = rng:next() })
end
```

## Item pickups

`BR.pickup` places item, ammo and health pickups, drops a player's item as one, and decides per
player who may take them.

```lua
-- a weapon spawn that comes back 30 s after it is taken
BR.pickup.spawn("Shotgun", { 0, 0, 30 }, { respawn = 30 })
BR.pickup.spawn("Ammo_Light", { 40, 0, 30 })

-- TTT: a dead player's item, which only traitors may take
local p = BR.pickup.drop(victim, slot)
traitor_items[__addr(p)] = true
BR.pickup.gate(function(ps, pk)
    if traitor_items[__addr(pk)] then return is_traitor(ps) end
end)

BR.pickup.on(function(ps, pk, item) print(BR.player.info(ps).display_name .. " took " .. tostring(item)) end)
```

| Function | Does |
| --- | --- |
| `class(what)` | the pickup class for a short name (`"Pistol"`, `"Ammo_Light"`, `"Health_Small"`), a pickup class name, an item class name (`"Weapon_Pistol"`) or a class |
| `spawn(what, position, opts)` | place one; opts `respawn` (seconds, 0 never), `once` (removed once taken), `multi`, and the item's tuning as `BR.player.tune` names it (`damage`, `speed`, `name`, `projectile`, `projectile_scale`, `colors`) |
| `drop(ps, slot, opts)` | take the item out of the slot and leave it where they stand (or `opts.position`), its tuning kept; it goes away once taken unless `opts.once = false` |
| `gate(fn)` | `fn(player, pickup)` returning false stops that player taking that pickup; it stays enabled for everyone else. Returns a remover |
| `on(fn)` | `fn(player, pickup, item)` after someone takes a pickup; `item` is the item class name, nil for ammo and health. Returns a remover |
| `list()` | every pickup in the world |

A pickup is taken through its `HandlePickupAttempt(Pawn)`, a Blueprint native event that the
Blueprint pickups override, so the game calls it through ProcessEvent and the gate's hook can
refuse it. A player standing in a pickup that refused them gets no new attempt until they step
out and back in. Bots never take pickups on their own: only a character its player controller
holds can, and a bot's is held by an AI controller.

Tested with bots on Release-EA3-CL-16507 (pickup attempts made from Lua): drop with tuning kept,
gate refusing and allowing, `on`, removal once taken, spawning ammo. A real player walking into
a pickup hasn't been seen through the gate yet.

## Bots

A bot is a player with no client behind it: a spawned player controller with its own
PlayerState. The game treats it as a player: it joins teams, respawns, owns bricks, chats under
its own name and has a full set of builder tools. Drive it with [`BR.act`](#player-actions).
`BR.player.list()` leaves bots out (it lists connected clients); client RPCs
(`BR.player.whisper`, `status`, ...) refuse them.

| | |
|--|--|
| `BR.bot.spawn(name, opts?)` | its PlayerState; `opts.team` (default -1, unaffiliated), `opts.weapons` (names, given on every spawn), `opts.respawn_after` (seconds, default 3; `false` for game modes that respawn players themselves), `opts.respawn = false` for no character yet |
| `BR.bot.list()` | every bot's PlayerState |
| `BR.bot.is_bot(ps)` | a controller, no client, not a server owner |
| `BR.bot.remove(ps)` | the character goes now, the bot on the next tick |
| `BR.bot.drive()` | restart the tick that drives bots; `spawn` does it, so it is only needed after a `BR_RELOAD`, for bots spawned before it |

A bot's character is driven by an AI controller of its own, which the server simulates locally:
movement input, view, crouch, sprint and weapons apply directly, under the game's own movement
rules, and other players see it like any character. The player controller keeps the bot's name,
tools and chat. The game does not respawn a bot, so `BR` does (`opts.respawn_after`). Its kills and
deaths fire `BR.event.on("death")` like anyone's; the game names no killer controller for a bot's
kill, so read `info.killer_player`, which `BR` resolves from the weapon or projectile too.

| | |
|--|--|
| `BR.bot.move(ps, x, y)` | walk in world direction (x, y) until told otherwise; (0, 0) stops |
| `BR.bot.move_to(ps, {x, y, z}, opts?)` | walk straight there; `opts.radius` (default 40), `opts.on_arrive(ps)`, `opts.on_fail(ps)` when it stops getting closer. Walls are not avoided |
| `BR.bot.path_to(ps, {x, y, z}, opts?)` | walk there along a [`BR.nav`](#navigation) path: around walls, up steps, jumping up ledges; finds a new path when stuck (three times), then `on_fail` |
| `BR.bot.stop(ps)` / `BR.bot.moving(ps)` | |
| `BR.bot.look(ps, yaw, pitch)` | degrees, yaw 0 is +x; `look(ps)` hands facing back to the walking direction |
| `BR.bot.look_at(ps, {x, y, z})` | from the character's eyes |
| `BR.bot.jump(ps)` | |
| `BR.bot.crouch(ps, on)` / `BR.bot.sprint(ps, on)` / `BR.bot.fly(ps, on)` | held until released; `fly` sets the movement mode itself, with no permission check |
| `BR.bot.give(ps, weapon)` | a weapon by name (`"Pistol"`, `"Longsword"`: the part after `BP_ItemPickup_`); returns its slot |
| `BR.bot.equip(ps, slot)` | switch to an inventory slot (0-based, as `BR.player.inventory` numbers them) |
| `BR.bot.fire(ps, on)` / `BR.bot.reload(ps)` / `BR.bot.weapon(ps)` | hold or release the trigger; reload; the weapon in hand. It fires where the bot looks |

```lua
local ps = BR.bot.spawn("Builder")
BR.act.say(ps, "hello")
BR.act.emote(ps, BR.act.EMOTE.Wave)
BR.act.place(ps, { position = { 0, 200, 6 }, size = { 5, 5, 6 }, color = { 255, 128, 0 } })
BR.bot.sprint(ps, true)
BR.bot.move_to(ps, { 400, 200, 25 }, { on_arrive = function(p) BR.act.say(p, "made it") end })

BR.bot.look_at(gunner, { 300, 0, 50 })
BR.bot.fire(gunner, true)
```

Weapon damage follows the game mode: a team whose settings turn weapon damage off (the
unaffiliated team, usually) takes none.

## Navigation

There is no navmesh in a brick world, so `BR.nav` samples the ground as it searches: a 20-unit
grid, each cell's floor found by a ray cast down, a sweep the size of a character for headroom, and
a sweep between cells for walls. Steps up to the character's step height (16) are walked, ledges up
to a jump (50) are jumped, drops up to 200 are fallen. The search spends a few hundred traces a
tick (about 10 ms; `opts.budget`) until it is done, so the path arrives a few ticks later.
Characters do not block paths.

| | |
|--|--|
| `BR.nav.find(from, to, done, opts?)` | `done(path)`: floor points `{x, y, z, jump = true?}` from `from` to `to`, straight runs merged; `done(nil)` when there is none within `opts.max_nodes` cells (default 3000). Returns a function that cancels it |
| `BR.nav.clear(from, to)` | whether a character could walk straight there (one sweep) |
| `BR.nav.CHARACTER` | the figure the paths are for: `radius`, `height`, `step`, `jump`, `drop` |

A brick placed this tick has no collision until the next one, so neither does the path.

### A baked graph

`BR.nav.find` searches the world each time. A baked graph is laid into the build once, saved with
it, and editable by circuits. Each node is a hidden, non-colliding Array Variable gate standing on
the floor, 40 units apart on a world-aligned grid. It holds 9 numbers: the cost of the edge to the
neighbouring node in each direction of `BR.nav.GRAPH_DIRECTIONS` (+x, -x, +y, -y, then the four
diagonals; 0 means no edge), then a marker. A circuit that sets an element (Set Array Element on
the node's variable) changes that edge for the next route: 0 closes it (a door, a hazard), a
larger cost makes routes avoid it.

| | |
|--|--|
| `BR.nav.bake(seed, opts?)` | flood out from `seed` over every cell a character can reach within `opts.radius` (default 1000) and place a node on each, over a few ticks; `opts.done(count)`. Returns a cancel function |
| `BR.nav.unbake(center?, radius?)` | remove nodes within `radius` of `center`, or all of them |
| `BR.nav.graph(reload?)` | the nodes in the world, cached; `true` reads the world again (after a bake) |
| `BR.nav.route(from, to)` | Dijkstra over the graph with the costs the gates hold now; floor points like `BR.nav.find`'s, or nil. Synchronous: no traces |
| `BR.bot.path_to(ps, target, { graph = true })` | a bot follows a graph route |

Node gates take up the space they stand in, so a brick can't be placed exactly where a node is.
[`examples/zombies.lua`](../examples/zombies.lua) is a horde of bots that hunt the nearest player:
straight at them when `BR.nav.clear`, along a path when not.

## Player actions

`BR.act` does what a player does by hand, through the same server functions the game client
calls. The game applies its own rules to them: permissions (a game mode team can take building
away), trust, quotas, ownership. They work on any PlayerState, a bot's or a connected player's.

Tool actions use the player's own builder tool (no need to wield it) and return the transaction
report it produced, the same shape as `BR.brick.transaction`'s; all zeros when the game refused.
`BR.brick.changes(report)` keeps the non-zero counters.

| | |
|--|--|
| `BR.act.place(ps, opts)` | Placer: `opts.position` (grid units, the brick's center), `asset` (default `PB_DefaultBrick`), `size` (half extents, procedural bricks), `orientation`, `color {r, g, b}`, `material` (a `BR.brick.MATERIAL` name), `alpha` (0 to 5, default 5), `count {x, y, z}` for a volume (as the placer's drag sends it: the game lays out `ceil(count / 2)` copies along each axis), `spacing {x, y, z}` (an extra gap), `signs {x, y, z}` (1 or -1, which way copies go) |
| `BR.act.place_prefab(ps, opts)` | Placer, as a client's paste: `opts.prefab` (a cached prefab's hash, from `BR.prefab.cached`), `position`, `orientation`, `count`, `spacing`, `preserve_ownership`. It sets the placer's current placeable and the copy size a client would send. The game limits how often a player pastes (`BR.Permission.Prefabs.BypassTimeout` lifts it); a paste refused for that leaves an empty report |
| `BR.act.hammer(ps, brick)` | Hammer: delete the brick |
| `BR.act.paint(ps, brick, opts)` | Painter: `opts.color`, `material`, `alpha`; only what is given changes |
| `BR.act.set_visible(ps, brick, visible)` | Applicator |
| `BR.act.set_collision(ps, brick, channels)` | Applicator: `BR.brick.ALL_COLLISION`, or 0 |
| `BR.act.wire(ps, from, to)` | Connector: `from`/`to` are `{ brick, type, port }`; disconnects instead if the wire exists |
| `BR.act.say(ps, message)` | chat as the player (`BR.event.on("chat")` sees it) |
| `BR.act.emote(ps, emote)` / `BR.act.stop_emote(ps)` | `emote` is a `BR.act.EMOTE` value: `Beckon`, `Clap`, `Dab`, `Facepalm`, `HatBow`, `Hug`, `Nod`, `Point`, `ShakeHead`, `Shrug`, `Sit`, `Think`, `TipHat`, `Wave` |
| `BR.act.interact(ps, brick, nearby?)` / `BR.act.stop_interact(ps)` | click a brick (a button stays held until `stop_interact`) |

```lua
local from = { brick = notGate, type = "BrickComponentType_Expr_LogicalNOT", port = "bOutput" }
local to = { brick = andGate, type = "BrickComponentType_Expr_LogicalAND", port = "bInputA" }
print(BR.brick.changes(BR.act.wire(ps, from, to)).WiresConnected)   -- 1
```

## Voice

Any player, a bot included, can be made to speak audio through voice chat. Players near the
talker's character hear it from there, as they would the player's own voice: distance, voice
effects, mutes and the voice chat permission all apply. The audio is Opus, as the game's own
voice is; ffmpeg makes it from any file:

```sh
ffmpeg -i speech.wav -ac 1 -ar 24000 -c:a libopus -frame_duration 20 -application voip speech.ogg
```

| | |
|--|--|
| `BR.voice.play(ps, path, opts?)` | say an Ogg Opus file; `opts.done(ps)` after the last frame. Returns a stop function |
| `BR.voice.say(ps, frames, opts?)` | say a list of Opus frames (20 ms each), sent one per 20 ms |
| `BR.voice.ogg_frames(path)` | the Opus frames in an Ogg Opus file |
| `BR.voice.FRAME_SECONDS` | 0.02, one frame |

Recording works the other way round: the bridge copies every frame the server routes, any
player's or `BR.voice`'s own, already Opus, so a clip is just those frames in an Ogg file.

| | |
|--|--|
| `BR.voice.capture(fn)` | `fn(ps, frame, position, burst)` for every frame anyone says; returns a stop function |
| `BR.voice.recorder(opts?)` | keep each player's last `opts.seconds` (default 60) of speech; returns a stop function |
| `BR.voice.recorded()` | `{ key, name, id, seconds }` per player recorded, including players who have left |
| `BR.voice.clip(who, path, opts?)` | write a player's recording (`who`: PlayerState, or a key from `recorded`) to an Ogg Opus file; `opts.seconds` for only the last stretch. Silence between bursts is left out. Returns the seconds written |
| `BR.voice.write_ogg(path, frames)` | any Opus frames as an Ogg Opus file |

```lua
BR.voice.recorder({ seconds = 120 })
-- later, on a report
for _, r in ipairs(BR.voice.recorded()) do
    if r.name == "Someone" then BR.voice.clip(r.key, "/srv/reports/someone.ogg", { seconds = 60 }) end
end
```

Recording players' voices may need their consent where your server or they are; tell them.

Needs the bridge mod built with `__voice_route`, `__voice_capture` and `__voice_take`
(native/build.sh). Speaking is **not yet heard on a real client**; recording has only captured
`BR.voice`'s own frames so far.

## NPCs

The game's own AI bots, spawned by Bot Spawn bricks. They are characters with an AI controller,
not players.

| | |
|--|--|
| `BR.npc.list()` | live NPC pawns (`BP_FigureV2_Bot_C`) |
| `BR.world.teleport(actor, x, y, z)` | `K2_TeleportTo`, keeps rotation; world units |

A `B_Bot_Spawn_Point` brick spawns an NPC on top of itself within a second. It is configured
through its component inputs (`BR.component.ports("BotSpawn")`): `BotName`, `BotScale`, `MoveTarget`,
`bActiveBot`, `bSpawnEnable`, `AggroRange`, `RunSpeed`, `GunSkill`, `HealthMultiplier`,
`bCanTargetPlayers`, ... Place the spawn brick with `owner = BR.player.owner_index()` to set them
(`BotScale` and `bActiveBot` tested):

```lua
local spawn = BR.brick.place(BR.brick.builder({ asset = "B_Bot_Spawn_Point", owner = BR.player.owner_index() }), 0, 80, 6)
BR.component.set_input(spawn, "BotSpawn", "BotScale", BR.wire.double(2))
BR.component.set_input(spawn, "BotSpawn", "bActiveBot", BR.wire.bool(false))
```

String inputs take `BR.wire.string`; any field, wire input or not, takes `BR.component.set`.

## Zones

A zone is the box a zone projector brick (`BP_ZoneProjector`) projects. It can hold water, wind,
building rules and occupancy gates. Zones are named by their projector's BrickHandle, and their
settings are that brick's `Component_Internal_AttachedZone` (`BR.zone.COMPONENT`): `bWater`,
`ZoneEndDistance`, `bDetectPlayers`, `OccupantCount` and so on, through `BR.component.get`/`set`.

| | |
|--|--|
| `BR.zone.list(grid?)` | every zone on a grid, or on all grids; looks at every brick (about 0.15 s for 4000), so keep the result |
| `BR.zone.is_zone(h)` | whether a brick projects a zone |
| `BR.zone.box(zone)` | `{ center, half, grid }`, in the grid's coordinates (world coordinates on the global grid) |
| `BR.zone.contains(zone, ch, box?)` | whether a character is in it; pass a `box` to check many characters against one zone |
| `BR.zone.occupants(zone)` | PlayerStates (bots included) whose characters are in it |
| `BR.event.on_zone(zone, fn)` | `fn(player, active, character)` on entering (`active` true) and leaving |

A character is in a zone when its capsule touches the box, which is how the game counts
`OccupantCount`. Its center doesn't have to be inside. On a dynamic grid the box moves and turns
with the grid. Membership is geometric, whatever the zone's detection settings or tag filter
say. `on_zone` is polled with the [movement](#movement) events, so it fires up to 0.1 s late. A
player already inside when the listener starts gets an enter. Dying, leaving the server, or the
zone's brick being removed counts as leaving, with no `character`.

Water works the same in the world's water and in a zone with `bWater` on: the character is moved
into a water physics volume (for zones, one shared stand-in volume) and swims, which is what
`BR.player.in_water` and `on_water` read.

```lua
local pool = BR.zone.list()[1]
BR.event.on_zone(pool, function(player, entered)
    if entered then BR.player.status(player, "no running by the pool") end
end)
```

The rest of `BRLuauEntityLibrary` is reflected and callable directly:

```lua
local W = StaticFindObject("/Script/Brickadia.Default__BRLuauWorldLibrary")
local E = StaticFindObject("/Script/Brickadia.Default__BRLuauEntityLibrary")
local cls = W:FindEntityType("Entity_Ball", BR.world.context())   -- Entity_Ball, Entity_Wheel_Caster, ...
local ball = BR.entity.spawn(cls, 0, 0, 300)
E:SetTransform(ball, { Rotation = { X = 0, Y = 0, Z = 0, W = 1 }, Translation = { X = 100, Y = 200, Z = 500 }, Scale3D = { X = 1, Y = 1, Z = 1 } })
E:GetVelocity(ball)
```

Attaching to the character actor itself works on the server but clients see the grid trail
loosely behind; attached to the skeletal mesh (at a socket), it holds rigidly, which is why
`attach` uses the mesh. Seen on a real client with a grid on `Part_Head`. Clients only take the
offset of the first attach: attaching again with a different offset (even after a detach) moves
it on the server but not on screen. To adjust a grid that is already on someone, move its
bricks within the grid instead (`tx.move`).

`SpawnEntity` with the type class `Entity_Ball_C` creates a `BP_Entity_Ball_C` actor. Entity
custom properties only exist as gates (`Exec_Entity_Set/Get/RemoveCustomProperty`); drive them
with a trigger and `BR.wire.string` keys.

## Chat channels

`BR.chat` delivers a chat line to chosen players only, as that player's own message (the game
sends each client a player's line with `ClientPushPlayerChatMessage(formatted, raw, sender)`).
That makes team, local, staff or private channels and ignore lists.

| | |
|--|--|
| `BR.chat.route(fn)` | `fn(player, message)` returns the PlayerStates that should get each line, or nil to leave it to the game; chat commands are left alone. Returns a stop function |
| `BR.chat.send(to, from, text, opts?)` | deliver `text` as a line from `from` to `to` (a PlayerState, a list, `"all"`); formatted as typed chat is unless `opts.raw` |
| `BR.chat.format(text)` | a message as the game formats typed chat: `"**hi** :heart:"` becomes `"<b>hi</> <emoji>heart</>"` |

```lua
-- team chat for lines starting with "!"
BR.chat.route(function(player, message)
    if message:sub(1, 1) ~= "!" then return nil end
    return BR.team.players(BR.player.team(player))
end)
```

A routed line never reaches the game's chat handling, so it isn't logged as `LogChat:` and
omegga's chat event doesn't see it. Tested with a bot: a routed line was kept out of the game's
chat and the next one went through; delivery to a real client is not yet seen.

## Timers

| | |
|--|--|
| `BR.timer.after(seconds, fn, opts?)` | call `fn` once, `seconds` from now (0 = next tick); returns a cancel function |
| `BR.timer.every(seconds, fn, opts?)` | call `fn` every `seconds` until it returns `false` or is cancelled; `opts.now` runs it at once too |
| `BR.timer.next_tick(fn, opts?)` | call `fn` at the start of the next tick |
| `BR.timer.now()` | seconds of game time counted so far |
| `BR.timer.cron(expr, fn, opts?)` | call `fn` on a wall-clock schedule, a cron expression (`"0 */2 * * *"`: every two hours on the hour; `"30 20 * * 5"`: Fridays at 20:30), until it returns `false` or is cancelled |
| `BR.timer.at("HH:MM", fn, opts?)` | call `fn` every day at that time |
| `BR.timer.cron_matches(expr, t?)` | whether `expr` matches `t` (an `os.date("*t")` table; now by default) |

`opts.owner` ties a timer to a PlayerState, another UObject or a brick handle, and the timer
ends quietly once that is gone: a player who left the game (their PlayerState stays valid for a
while, so leaving the player list is what counts), a destroyed actor, a removed brick. Timers run
on the game thread at the start of a tick, in the order they fall due, so ticks are the finest
grain. A repeating timer keeps to its schedule rather than drifting by a tick each time. Unlike
UE4SS's `LoopAsync`, the callback may use `BR`.

Schedules (`cron`, `at`) follow the server's local clock, or UTC with `opts.utc`, and take
`opts.owner` too. Cron fields are minute, hour, day of month, month and day of week (0-6 from
Sunday, 7 also Sunday); each is `*`, a number, `a-b`, `*/n`, `a-b/n` or a comma list. With both
day fields restricted, either matching is enough, as in cron. Schedules are checked once a
minute, so `fn` runs within a tick or so of the minute starting, never twice in one minute, and
not in the minute the schedule was made.

```lua
-- a restart warning every day at 03:55, five minutes before omegga's auto-restart
BR.timer.at("03:55", function() BR.server.chat("Restarting in 5 minutes") end)
```

```lua
BR.event.on_spawn(function(player)
    BR.timer.every(1, function()
        local ch = BR.player.character(player)
        if not ch then return false end
        local hp, max = BR.player.health(ch)
        BR.player.set_health(ch, math.min(max, hp + 1))
    end, { owner = player })
end)
```

## Chat commands

The game handles a typed `/name args` with its own command system. omegga sees a call to a
command the game doesn't have, and the ue4ss plugin hands the ones a mod declares to Lua. A mod
declares each command in its `doc.json`, as an omegga plugin does:

```json
{ "commands": [{ "name": "heal", "description": "Heal yourself or someone", "args": [{ "name": "player" }] }] }
```

Only declared names reach Lua, and omegga tells the player any other doesn't exist. A built-in
command runs before omegga sees it, so a mod can't take its name. A world can also take commands
without Lua: the Chat Command gate, wired to what it should do (and to a Send Custom Event gate
for `BR.event.on_custom` to hear).

| | |
|--|--|
| `BR.command.register(name, fn, opts?)` | `fn(player, args, ctx)` for `/name`, declared in the mod's doc.json; returns a function that unregisters it |
| `BR.command.list(player?)` | `{ name, aliases, description, usage, permission }` for each command, sorted; with `player`, only those they may use |
| `BR.command.builtin(name)` | whether the game has a command of that name (which a mod can't take) |
| `BR.command.split(text)` | the words of a line, `"double quotes"` keeping spaces |

`args` are the words after the name, `ctx` is `{ name, raw, reply }`: `raw` is the text after the
name and `ctx.reply(text)` whispers back (to the log for a bot). Names match without regard to
case. Options: `permission` (a [BR.perm](#permissions) permission the player needs, or they're
told they can't), `aliases` (declared too), `description`, `usage`. A handler that errors is
logged and the player is told it failed. Underneath, `Omegga.on("cmd:<name>", fn)` gets the
player's name and the words as omegga split them.

```lua
BR.perm.define("myplugin.heal", { roles = { "Moderator", "Admin" } })
BR.command.register("heal", function(player, args, ctx)
    local target = args[1] and BR.player.find(args[1]) or player
    local ch = target and BR.player.character(target)
    if not ch then return ctx.reply("nobody to heal") end
    BR.player.set_health(ch, select(2, BR.player.health(ch)))
end, { permission = "myplugin.heal", usage = "/heal [player]" })
```

Tested on Release-EA3-CL-16507 with a bot, through the call omegga makes: arguments with quotes
and an alias in other case reached the handler, a command needing a missing permission was
refused, and after unregistering the name did nothing.

## Moderation

| | |
|--|--|
| `BR.mod.kick(ps, reason?, by?)` | disconnect a player (bots too); the game announces "... was kicked by server (reason)" |
| `BR.mod.ban(who, opts?)` | ban an account (a PlayerState or account id) and kick them if on: `duration` seconds (default 100 years: the game's bans always expire), `reason`, `by` (PlayerState) |
| `BR.mod.unban(who)` | lift it |
| `BR.mod.banned(who)` | `{ reason, by, created, expires }` (Unix seconds) or nil |
| `BR.mod.bans()` | every ban, `{ [id] = { reason, by, created, expires } }`, from `Saved/Server/BanList.json` (written a moment after a change) |
| `BR.mod.on_join(fn)` | `fn(player)` for everyone who joins from now on, bots included; return `false` or a reason to kick them; returns a function that removes it |
| `BR.mod.guid(id)` | an account id as the game's `BRGuid` table |

The game refuses banned accounts when they connect. Join gates run as a player appears: a real
client's login is hooked, and new names in the player list are also checked every 0.1 s, which
covers bots (they never log in). Gates run newest first, and the first to refuse decides.

```lua
BR.mod.on_join(function(player)
    if not BR.perm.has(player, "myplugin.whitelisted") then return "This server is whitelist only" end
end)
BR.command.register("tempban", function(player, args, ctx)
    local target = BR.player.find(args[1] or "")
    if not target then return ctx.reply("no such player") end
    BR.mod.ban(target, { duration = (tonumber(args[2]) or 60) * 60, reason = args[3], by = player })
end, { permission = "BR.Permission.Ban", usage = "/tempban <player> [minutes] [reason]" })
```

Tested on Release-EA3-CL-16507: a gate kicked a bot by name with its reason and let another stay;
a ban on a made-up account read back with its reason and duration and showed in the ban list,
and unbanning lifted it. Gating a real client's join is not yet tried.

## Permissions

The game's permissions are gameplay tags (`BR.Permission.Fly`,
`BR.Permission.Building.Placer.PlaceBricks`, ...) that roles allow or forbid. Every check the
game makes goes through `BRPlayerState::HasPermission`, which the bridge hooks, so an override
set here changes what the game itself lets that player do. A tag covers the tags under it:
forbidding `BR.Permission.Building` stops every kind of building, unless a more specific tag
has an override of its own.

Plugins can also define their own permissions (`"myplugin.vip"`), granted per role and per
player, with the same parent rule.

| | |
|--|--|
| `BR.perm.has(ps, name)` | whether the player has a game tag or a defined plugin permission |
| `BR.perm.set(ps, name, state)` | force it for one player: `true` allows, `false` forbids, `nil` removes the override |
| `BR.perm.get(ps, name)` / `BR.perm.clear(ps)` | the player's own override, or nil / drop all of their overrides |
| `BR.perm.define(name, opts?)` | a plugin permission: `default` (bool, default false), `roles` (role names that have it), `description` |
| `BR.perm.set_role(role, name, state)` | grant or forbid a plugin permission for a role (`nil` removes it) |
| `BR.perm.defined()` / `BR.perm.game_tags()` | the plugin permissions / every tag a role can set |
| `BR.perm.trace(fn)` | `fn(player, tag, allowed)` for every check the game makes; returns a stop function |
| `BR.perm.GAME_PREFIX` | `"BR.Permission"`, the prefix of every game tag |

A plugin permission is decided by the player's own override, then the server owner (who has
everything), then the highest role they have that grants or forbids it, then the roles named in
its definition, then its default. Overrides are saved by account in `BR.store` `permissions`
and come back when the player rejoins, game tags included. A bot's last until it leaves (bots
have no account).

Use `BR.perm.trace` to find what an action checks: placing a brick checks
`Building.Placer.PlaceBricks` among a dozen others, hammering checks `Building.Hammer.DeleteBricks`,
chatting checks `Chat` (and a forbidden message shows in the log as `[blocked]`).

```lua
-- no building for anyone without the plugin's builder permission
BR.perm.define("myplugin.builder", { roles = { "Moderator", "Admin" } })
BR.event.on("place", function(player)
    if not BR.perm.has(player, "myplugin.builder") then return false end
end)

-- a muted player
BR.perm.set(ps, "BR.Permission.Chat", false)
BR.perm.set(ps, "BR.Permission.VoiceChat", false)

-- what does flying check?
local stop = BR.perm.trace(function(player, tag, allowed) print(tag, allowed) end)
```

The server enforces overrides. A player's client also checks its own permissions for its
interface, from its roles, so a forbidden tool still shows (and the server refuses it), and a
permission granted only by override may not be offered in the client's menus. **Not yet tried
with a real client.**

Tested on Release-EA3-CL-16507 with a bot: forbidding `BR.Permission.Building` stopped a placement
(the trace saw `PlaceBricks` refused) and removing it let the next one through; a forbidden chat
was logged as `[blocked]`; a granted admin permission read true; a plugin permission followed its
default, a role grant, a player override and clearing in turn.

## Shared state

`BR.state` holds named values (anything JSON can hold) and tells watchers when one changes:
other code in the same Lua state, screen elements, and omegga plugins, which see each change as
the Lua event `state` (`{ key, value }`; `ue4ss:state` on omegga, or by subscription).

| | |
|--|--|
| `BR.state.set(key, value, { persist? })` | set (nil removes) and tell watchers if it changed; `persist` saves the key with the world from then on (BR.store `state`) |
| `BR.state.get(key)` / `BR.state.all()` | |
| `BR.state.watch(key, fn, { now? })` | `fn(value, old, key)` on each change of `key` (`"*"`: any); `now` calls it once at once. Returns a stop function |
| `BR.state.bind_ui(key, element, render, motion?)` | keep a [screen element](#screen-elements-and-transitions) in step: `render(value)` returns the options to change |

```lua
local label = BR.ui.text("all", { anchor = "top", y = 20, size = 28 })
BR.state.bind_ui("score.red", label, function(v) return { text = "Red " .. (v or 0) } end)
BR.state.set("score.red", 3, { persist = true })
```

Tested: watchers saw `nil -> 1 -> 2`, setting an equal value told nobody, and a persisted key
was saved in the `state` store.

## Storage

`BR.store` keeps small tables across restarts in the ue4ss plugin's omegga storage (one entry,
`lua:<name>`, per name), so they're kept and backed up with the rest of omegga's data. Tables
from the JSON files earlier versions wrote to `Saved/LuaStore/` are copied in once, the first
time the plugin starts.

Lua can't wait for omegga on the game thread, so each Lua state holds a copy of every store:
omegga sends it when the bridge connects, and saves go back in the background (and again after
a reconnect, if omegga missed them). Mods load before omegga connects, so reading a store before
then is an error rather than an empty table a later save would write over: open stores in
`BR.store.on_ready(fn)`, or lazily, when a player does something. Separate mods are separate Lua
states with their own copies; two mods saving one name get whichever saved last.

| | |
|--|--|
| `BR.store.ready()` | whether the stores have arrived |
| `BR.store.on_ready(fn)` | run `fn` once they have (now, if they have) |
| `BR.store.load(name)` | a copy of the table saved under `name`, or `{}` |
| `BR.store.save(name, table)` | save it |
| `BR.store.delete(name)` | forget it |
| `BR.store.open(name, opts?)` | `s` with `s.data` (the table), `s.save()`, `s.get(key)`, `s.set(key, value)` (saves) |
| `BR.store.view(name, opts?)` | `open` once the stores have arrived; before then an empty store with `pending = true` whose save is an error, for code that may run first (a permission check) |

Names are letters, digits, `_`, `-` and `.`. Values are what JSON holds: strings, numbers,
booleans and tables (a table with keys 1..n is saved as a list).

```lua
local scores
BR.store.on_ready(function() scores = BR.store.open("myplugin-scores") end)
-- later, when someone scores
scores.set(BR.player.id(ps), (scores.get(BR.player.id(ps)) or 0) + 1)
```

A store whose layout changes takes `opts.version` and `opts.migrate`: data saved at an older
version runs through each step up to the current one, in order, and is saved at once. A step
changes the table it gets or returns a new one. Data saved before the mod used versions counts
as version 1, and a store with nothing saved starts at the current version. The version is kept
with the data as `__version`, out of `s.data`. Data from a newer version is an error rather than
being overwritten by an older mod.

```lua
local s = BR.store.open("arena", { version = 3, migrate = {
    [2] = function(d) d.scores = d.points; d.points = nil end,   -- renamed
    [3] = function(d) return { players = d } end,                -- nested
} })
```

## Lua logic in a circuit

There is no Lua gate, but two pieces make one: a circuit sends a custom event (the Send Custom
Event gate) and Lua answers it with `BR.event.on_custom`, sending results back with
`BR.event.custom(name).send(...)` to the circuit's Receive Custom Event gates; scripted bricks
(`BR.behavior.define`) give a brick type its own Lua state and lifecycle. Together a mod can make a
brick that takes inputs from wires and drives outputs, with Lua deciding in between.

## Movers, bot behaviours, cameras and languages

**Movers.** `BR.mover.path(entity, points, opts?)` moves an entity (a dynamic grid such as a
platform or a door, or any other entity) through waypoints `{ {x, y, z}, ... }` at `opts.speed`
units a second (200): `mode` `"once"` (default), `"loop"` or `"ping_pong"`, `wait` seconds at
each point, `rate` moves a second (60; at 30 a rider sees it judder), `on_arrive(index)`. Each step is an entity move
transaction, the change a player's tools make, so clients see it; turn physics off on what moves
(`tx.physics(e, false)`). Returns `m` with `m:stop()`, `m:pause()`, `m:resume()`,
`m.position`.

**Bot behaviours.** `BR.bot.patrol(ps, points, opts?)` walks a round again and again (`wait` at
each point, `pathfind = true` to go around walls); `BR.bot.follow(ps, target, opts?)` keeps within
`distance` (150) of another player or bot. Both return a stop function.

**Cameras.** `BR.player.fade(ps, from, to, seconds, color?, opts?)` fades the screen (alpha 0 to 1,
default black; `opts.hold`, `opts.audio`). `BR.player.view_from(ps, actor, { blend })` shows the
world from another actor (a camera entity, a character, a vehicle) and `BR.player.view_reset(ps)`
gives the player their own view back. Client RPCs: connected players only, on the checklist. A
per-player field of view or sky has no server route.

## Math

`BR.math` is vector, quaternion, rotator and angle math in plain Lua, for code that runs often
(every tick, every player) and shouldn't call into the engine. The conventions are Unreal's, and
the results match `KismetMathLibrary` (an acceptance check compares them):

- Units are Unreal units: X forward, Y right, Z up.
- A rotator is `{ Pitch, Yaw, Roll }` in degrees, the game's `FRotator`.
- Euler angles are a vector `(Roll, Pitch, Yaw)` in degrees, as `FQuat::Euler`.
- `q1 * q2` is `q2`'s rotation, then `q1`'s.

Constructors take numbers, an array (`{ x, y, z }`, what BR functions use), a table with
`X/Y/Z` fields (what game functions return) or a value of the same type, so both kinds of input
work. `:ue()` gives the table a game function takes, `:array()` the array BR takes, `:unpack()`
the numbers.

| Vectors | |
|--|--|
| `BR.math.vec(x, y, z)` / `vec(t)` | a vector; `ZERO`, `FORWARD`, `RIGHT`, `UP` |
| `a + b`, `a - b`, `-a`, `a * n`, `n * a`, `a / n`, `a * b`, `a / b` | arithmetic; two vectors work per component |
| `a:dot(b)`, `a:cross(b)` | |
| `a:length()`, `a:length_squared()`, `a:length_2d()`, `a:distance(b)`, `a:distance_squared(b)` | |
| `a:normalized()` | unit length, or zero for a (nearly) zero vector |
| `a:lerp(b, t)`, `a:angle_to(b)` | angle in degrees, 0..180 |
| `a:project_on(dir)`, `a:project_on_plane(normal)`, `a:reflect(normal)` | |
| `a:near(b, tolerance?)`, `a:is_zero(tolerance?)` | |
| `a:rotator()`, `a:quat()` | the rotation facing along it (roll 0) |

| Quaternions | |
|--|--|
| `BR.math.quat(x, y, z, w)` / `quat(t)` / `quat()` | a quaternion (from a rotator too); no arguments or `IDENTITY`: no rotation |
| `BR.math.quat_euler(roll, pitch, yaw)` / `quat_euler(vec)` | from Euler angles in degrees |
| `BR.math.quat_axis_angle(axis, degrees)` | about an axis |
| `BR.math.quat_between(a, b)` | the shortest rotation taking direction `a` onto `b` |
| `BR.math.quat_look(forward, up?)` | facing `forward`, its up as near `up` (default world up) as that allows |
| `BR.math.quat_from_axes(x, y, z)` | from its forward, right and up unit vectors |
| `q1 * q2`, `q * v` | compose; rotate a vector |
| `q:rotate(v)`, `q:unrotate(v)` | |
| `q:inverse()`, `q:normalized()`, `q:dot(q2)` | |
| `q:forward()`, `q:right()`, `q:up()` | its axes |
| `q:angle()`, `q:axis()`, `q:axis_angle()` | in degrees |
| `q:angle_to(q2)`, `q:slerp(q2, t)` | degrees between them (0..180); the short way between them |
| `q:rotator()`, `q:euler()` | conversions |

| Rotators | |
|--|--|
| `BR.math.rot(pitch, yaw, roll)` / `rot(t)` | a rotator, from degrees or a `Pitch/Yaw/Roll` table |
| `r1 + r2`, `r1 - r2`, `-r`, `r * n` | per angle |
| `r:quat()`, `r:euler()` | conversions |
| `r:forward()`, `r:right()`, `r:up()` | its axes |
| `r:rotate(v)`, `r:unrotate(v)`, `r:normalized()`, `r:angle_to(r2)`, `r:slerp(r2, t)` | |

| Angles and numbers | |
|--|--|
| `BR.math.rad(deg)`, `BR.math.deg(rad)` | also `D2R`, `R2D` |
| `BR.math.normalize_angle(a)` | to (-180, 180] |
| `BR.math.clamp_angle(a)` | to [0, 360) |
| `BR.math.delta_angle(a, b)` | the shortest turn from `a` to `b` |
| `BR.math.lerp_angle(a, b, t)` | from `a` towards `b` the short way |
| `BR.math.lerp(a, b, t)`, `BR.math.clamp(v, lo, hi)` | |
| `BR.math.transform(location, rotation?, scale?)` | an `FTransform` table for game functions |

```lua
local M = BR.math
-- turn a bot towards a point, at most 5 degrees per call
local ch = BR.player.character(bot)
local want = (M.vec(target) - M.vec(ch:K2_GetActorLocation())):rotator().Yaw
local now = ch:K2_GetActorRotation().Yaw
BR.bot.look(bot, now + M.clamp(M.delta_angle(now, want), -5, 5))

-- a point 200 units in front of an entity, whichever way it's turned
local t = entity:GetTransform()
local front = M.vec(t.Translation) + M.quat(t.Rotation):forward() * 200
```

Tested on Release-EA3-CL-16507 against `KismetMathLibrary` with random inputs: Euler, rotator and
quaternion conversions, rotating vectors, composing, slerp, the rotation between two vectors,
look rotations, axes, angles between rotations and angle normalizing agree to floating point
(angles to about 1e-5 degrees, where the engine works in single precision).

## Small helpers

**Waiting in a timer.** `BR.timer.async(fn, opts?)` runs `fn` as a coroutine; inside it,
`BR.timer.sleep(seconds)` pauses (game time) and comes back on the game thread. Returns a
cancel function; `opts.owner` as for other timers.

```lua
BR.timer.async(function()
    for i = 3, 1, -1 do BR.server.chat(tostring(i)) BR.timer.sleep(1) end
    BR.world.next_round()
end)
```

**Chat filters.** `BR.chat.limit(opts?)` mutes a player who sends more than `messages` (5)
lines in `per` seconds (10) for `mute` seconds (30); commands don't count. `BR.chat.censor(words,
opts?)` replaces whole words (any case) with `opts.replace` (`"■■■"`: asterisks would be read as
markdown and vanish) or refuses the line with `opts.block`. Both return a stop function.

**Config.** `BR.config.open(name, defaults)` reads `LuaConfig/<name>.json` in omegga's data
directory (the plugin's launch env names it): `c.get(key)`,
`c.all()`, `c.path()`. The file is written with the defaults the first time, and settings a later
version adds are filled in, so it always lists every setting. Edits take effect without a
restart (the file is checked at most every 2 s). Unlike `BR.secrets`, it's the mod's own
settings with defaults; secrets have none and are never written.

**Environment.** `BR.env.set(group, values)` changes settings of a group (`sky`, `ground`,
`water`, `ambience`, `space`, `studio`, `terrain`) through the group's own setters, as the Set
Environment Property gate does: `BR.env.set("sky", { TimeOfDay = 9.5, Rain = 0.5 })` (time of
day is in hours). An unknown setting is an error before anything changes.
`BR.env.get(group, setting)` reads one back (a colour as `{ R, G, B, A }`), and
`BR.env.settings(group)` lists the names a group takes. A world without a group (most have no
studio or terrain) says so. Tested on the server; whether clients see each one is on
docs/client-checks.md.

**Text in the world.** `BR.label.create(position, opts)` puts text at a point (a small brick
with no collision and a Text Display component): `text`, `billboard` (`"full"`, the default,
always faces the viewer; `"in_plane"`; `"none"`), `color`, `outline` and `outline_color`, `scale`,
`offset`, `foreground`, `material` (`"unlit"` reads the same in any light; `"glow"`,
`"metallic"`, ...). `l:set(changes)`, `l:remove()`, `l.text`. The text is rich text:
`<b>`, `<color="f00">...</>` and Font Awesome icons with `<icon>check</>`. Seen on a client on
Release-EA3-CL-16507.

**World lifecycle.** `BR.event.on_ready(fn)` runs when the world is ready, at once if it is now,
and after every world load. `BR.event.on_unload(fn)` runs when the previous world is gone, just
before the next `on_ready`. It comes after the fact: the engine runs no script as a world is torn
down, so keep state in `BR.store` or `BR.db` as it changes. Both are checked once a second.

**Data per world.** `BR.server.world()` names the current world (its path under `Saved/Worlds`),
and `BR.store.for_world(name, opts?)` is a store kept for that world, apart from other worlds'
and back when it loads again.

**Calling another mod.** `Omegga.invoke(name, args, fn)` calls a handler another Lua mod
registered with `Omegga.handle`; `fn(ok, result)` runs later on the game thread. Mods are
separate Lua states, so the call goes through the ue4ss plugin.

**The game's AI bots.** `BR.npc.on_spawn(fn)` (within half a second; ones alive when first
called don't count) and `BR.npc.on_death(fn)` (with the death event's info). `BR.npc.list()`
leaves out destroyed ones.

**Item and seat events.** `BR.event.on("equip", fn)` gets `{ character, item, previous }` when a
player's item in hand changes (class names, nil for none); `"seat"` gets `{ character, brick,
active }` when they sit in or leave a seat. Both are polled with the movement events (0.1 s).
Equip was tested with a bot; seats are on the checklist (a bot's interaction didn't seat it).

## Removal signal

`BR.watch.removed(target, fn)` calls `fn(target)` once when a brick (its handle) or an entity or
other actor is gone, however it went: hammered, deleted by a selection, cleared, replaced by a
load or a transaction, removed by a gate, destroyed. It is checked five times a second, so the
call comes within about 0.2 s. A removed brick's handle can't be read by then, so keep what `fn`
needs to know. Returns a function that stops watching; `BR.watch.count()` says how many are
watched.

An actor counts as gone as soon as it is destroyed: the game marks its object as garbage at
once, though UE4SS's `IsValid` stays true until the garbage collector runs.

```lua
local door = BR.brick.place(builder, x, y, z)
BR.watch.removed(door, function() BR.server.chat("The vault door is gone!") end)
```

## Profiling

`BR.profile` times every callback BR runs for a mod (event handlers, ticks, timers, hooks,
after-hooks, chat commands) on a steady clock, by kind and by the handler's source file and line,
so a slow handler points at its mod. Off, it costs one check per callback.

| | |
|--|--|
| `BR.profile.start()` / `stop()` / `reset()` / `running()` | |
| `BR.profile.report(opts?)` | slowest in total first (`opts.limit`, default 20): `{ kind, source, calls, total_ms, avg_ms, max_ms }` |
| `BR.profile.sample(seconds, fn, opts?)` | profile for a while, then `fn(report)` |
| `BR.profile.measure(name, fn, ...)` | run and record a mod's own work under `name` |

```lua
BR.profile.sample(10, function(report)
    for _, e in ipairs(report) do
        print(string.format("%-20s %-40s %6d calls %8.2f ms (max %.2f)", e.kind, e.source, e.calls, e.total_ms, e.max_ms))
    end
end)
```

## Targets

`BR.target.resolve(actor, spec, opts?)` turns what a player typed into players, the same way in
every mod. Returns the list, or nil and a message to show them.

- Selectors: `@all` (`@a`), `@me` (`@s`), `@others` (`@o`), `@nearest` (`@p`), `@random`
  (`@r`), `@team` (`@t`, the actor's team), `@team:<name>`, `@alive`, `@dead`.
- Otherwise an account id, or a name: an exact display or account name wins, then the names
  starting with what was typed, then the names containing it.
- Players with the `target.immune` permission are left out unless they're the actor or the
  actor has `target.bypass_immunity` (give admins immunity with
  `BR.perm.set_role("Admin", "target.immune", true)`). `opts.immunity = false` skips this.
- `opts.one` (or `BR.target.one`) wants exactly one player and otherwise names the candidates;
  `opts.bots` includes bots.

```lua
BR.command.register("slay", function(ps, args, ctx)
    local list, err = BR.target.resolve(ps, args[1] or "@me")
    if not list then return ctx.reply(err) end
    for _, p in ipairs(list) do
        local ch = BR.player.character(p)
        if ch then BR.player.kill(ch) end
    end
end, { permission = "myplugin.slay" })
```

## Build regions

`BR.region` gives areas of the world their own build rules: plots that belong to players
(bought, won, assigned), areas nobody builds in, bans on bricks or components, and an override
for admins. Regions are saved, so they survive restarts.

```lua
-- a plot a player bought
BR.region.define("plot-12", { box = { min = { 0, 0, 0 }, max = { 800, 800, 600 } }, owners = { buyer } })
BR.region.add_owner("plot-12", friend)

-- spawn: nobody builds; the rest of the world: only in your plots
BR.region.define("spawn", { box = { min = { -400, -400, 0 }, max = { 400, 400, 400 } }, build = "nobody" })
BR.region.set_default("nobody")

-- no cannons anywhere, no logic gates in the arena
BR.region.ban("assets", "B_2x2_Cannon")
BR.region.define("arena", { box = arena_box, build = "everyone", ban_components = { "BrickComponentType_Expr_LogicalAND" } })

-- tidy a plot when its owner leaves for good
BR.region.clear("plot-12")                                -- everything
BR.region.clear("plot-12", { asset = "B_2x2_Cannon" })   -- or one kind of brick
```

| | |
|--|--|
| `define(name, opts)` | create or replace a region: `box = { min, max }` or `boxes = { ... }` (grid units), `owners` (player ids or PlayerStates), `build` (`"owners"` by default, `"nobody"`, `"everyone"`), `copy` (anyone may select and copy there), `ban_assets`, `ban_components`, `message` (what a refused player sees) |
| `get(name)`, `list()`, `remove(name)` | |
| `add_owner(name, ps)`, `remove_owner(name, ps)` | a player id or PlayerState |
| `at({x, y, z})` | the regions containing a point |
| `set_default(rule)` | outside every region: `"everyone"` builds (default) or `"nobody"` |
| `ban(kind, names)`, `unban(kind, names)` | ban `"assets"` or `"components"` everywhere |
| `allows(ps, { min, max })` | whether a player may build in a box: true, or false and the region in the way |
| `bypass(ps, on)` | let one player build anywhere until turned off; the `region.bypass` permission does the same for a role (`BR.perm.set_role("Admin", "region.bypass", true)`) |
| `on_refused(fn)` | `fn(player, info)` on each refusal: `info.action`, `info.region`, `info.zone` or `info.banned`, `info.removed`; set `info.quiet = true` to stop the default message |
| `zone_rule(fn)` | build rules from zone bricks: `fn(zone, player, action)` for each world-grid zone a build overlaps; see below |
| `refresh_zones()` | take the zone list again now (it is kept for 10 seconds) |
| `bricks(name, filter?)`, `clear(name, filter?)` | the bricks touching a region, or remove them: `filter.asset`, `filter.component` (a name or list), `filter.owner` (a brick owner index). `clear` returns how many went |

What's checked, before the game acts:

- **Placing**, by the full extent of what lands. A dragged volume counts by every copy it lays
  out (the game puts `ceil(count / 2)` copies along each axis, `2 * (size + spacing)` apart, in
  the drag's direction), and each brick by its real size and rotation. A placement that only
  touches a region's face is fine, so owners can build right up to a border.
- **Prefabs**: the bricks are only known once they are down, so they are checked one by one
  right after, and the whole paste is removed if any brick breaks a rule (`info.removed` says
  how many). A paste anchored inside a forbidden region is refused at once.
- **Deleting** (hammer, the placer's delete mode), **painting**, **applicator** changes
  (adding a banned component is refused; pasting one onto a brick strips it), **resizing** (by
  the new size too) and **rotating**.
- **Selecting** in a region the player can't build in, unless the region has `copy`. That keeps
  others' bricks out of cut, delete and copy; a selection delete or cut with its own box is
  checked by that box.
- **Wiring** to a brick in such a region.

Bans apply to owners as well; only the bypass gets past them. Regions cover the world grid;
bricks on dynamic grids (vehicles, contraptions), entities moved with the grab tool and things
spawned by gates in the world aren't checked. Changes made through `BR.brick` and transactions
are the mods' own and aren't checked either.

### Rules from zone bricks

`BR.region.zone_rule(fn)` lets a mod decide who builds in the zones Zone Projector bricks
project, so a builder lays out plots in game. `fn(zone, player, action)` runs for each zone on
the world grid a build overlaps, with `zone = { brick, box = { min, max }, tag, building }`:
`tag` is the zone's tag filter and `building` its building zone flag, either of which a mod can
use to pick its zones. It returns `true` to allow the build (counting as a region, so a
`"nobody"` default doesn't apply), `false` and an optional message to refuse it, or `nil` when
the zone has no say. Regions are checked as well. The rule isn't saved: set it at load. Zones
are found by walking the world grid's bricks, so the list is kept for 10 seconds;
`BR.region.refresh_zones()` takes it again at once.

```lua
BR.region.zone_rule(function(zone, ps)
    if zone.tag ~= "plot" then return nil end
    return BR.perm.has(ps, "plots.build"), "Plots are for members"
end)
```

Tested with bots on Release-EA3-CL-16507: single bricks and dragged rows (refused when reaching
in, allowed when touching), the bypass and owners, an asset ban, a component ban (placed and
taken back out), hammer and paint refusals, box selection, prefab pastes anchored inside and
reaching in from outside (removed whole), `clear` with filters, and regions coming back after a
restart; a zone rule refusing a bot in a tagged zone and letting it build outside. Wiring,
resizing and the applicator haven't been run.

## SQLite databases

`BR.db.open(name)` is a SQLite database for what outgrows a JSON store: logs, history,
leaderboards over time. Each name is a file, `Saved/LuaDatabases/<name>.sqlite`.

| | |
|--|--|
| `d.exec(sql, fn?)` | a script of statements (a schema); `fn(ok, err)` |
| `d.run(sql, params?, fn?)` | one statement; `fn(ok, { changes, last_id })` |
| `d.query(sql, params?, fn)` | `fn(ok, rows)`, rows as `{ column = value }` tables |

`params` fill the statement's `?`s: numbers, strings, booleans (1 and 0). Queries run in the
ue4ss omegga plugin (Node's built-in SQLite), and the game thread can't wait for an answer, so
each takes a callback, which runs on the game thread a tick or two later. Calls on one
database run in the order made. A failed `exec` or `run` without a callback is reported in
omegga's console; a failed call's callback gets `false` and the SQLite error.

```lua
local h = BR.db.open("history")
h.exec("create table if not exists kills (killer text, victim text, at integer)")
BR.event.on("death", function(ps, info)
    local killer = info.killer_player and BR.player.info(info.killer_player).display_name or "the world"
    h.run("insert into kills values (?, ?, ?)", { killer, BR.player.info(ps).display_name, os.time() })
end)
h.query("select killer, count(*) as n from kills group by killer order by n desc limit 5", {}, function(ok, rows)
    for i, r in ipairs(rows) do BR.server.chat(i .. ". " .. r.killer .. " " .. r.n) end
end)
```

## Secrets

`BR.secrets` gives mods values the server admin supplies (webhook URLs, API keys, tuning)
without putting them in the mod's code or its store. They live in `Saved/LuaSecrets.json`,
which the admin edits and nothing in Lua writes:

```json
{ "discord.webhook": "https://...", "arena.rounds": 5 }
```

| | |
|--|--|
| `BR.secrets.get(key, default?)` | the value, or `default` |
| `BR.secrets.require(key)` | the value, or an error naming the key and the file |
| `BR.secrets.path()` | where the file is |

The file is read again when it changes, so an edit takes effect without a restart. Keys are any
strings; a dotted prefix per mod keeps them apart.

## Metrics

`BR.metrics` publishes Prometheus metrics from Lua. Each update goes to the omegga plugin, which
keeps them in its own registry, so they are scraped from omegga's metrics endpoint as
`omegga_plugin_ue4ss_<name>` (nothing is recorded when omegga's metrics are off).

| | |
|--|--|
| `BR.metrics.counter(name, opts?)` | `c.inc(n?, labels?)`, `c.reset()` |
| `BR.metrics.gauge(name, opts?)` | `g.set(v, labels?)`, `g.inc(n?, labels?)`, `g.dec(n?, labels?)`, `g.reset()` |
| `BR.metrics.histogram(name, opts?)` | `h.observe(v, labels?)`, `h.reset()`; `opts.buckets` are upper bounds |

`opts`: `help`, and `labels`, the label names its updates may use (omegga needs them declared).
Names are lowercase letters, digits and underscores, and a name keeps the kind it was first used
as. An update's `labels` is a table of strings, numbers or booleans. Every update is one message to omegga,
so for something that changes every tick, count in Lua and publish now and then. Tested: a
labelled counter and a gauge set from Lua came out of omegga's scrape as
`omegga_plugin_ue4ss_<name>{...,plugin="ue4ss"}`.

```lua
local kills = BR.metrics.counter("arena_kills", { help = "Kills in the arena", labels = { "weapon" } })
BR.event.on("death", function(player, info) kills.inc(1, { weapon = info.weapon or "none" }) end)
```

## Calling any UFunction

When every parameter is a reflected type, call it directly: `obj:FunctionName(args...)`. When
one is an opaque struct, use the raw path:

| | |
|--|--|
| `BR.raw.call(target, class, fn, args)` | `args` maps param names to bytes; returns a table of each param's bytes after the call. `class` is a Brickadia class or `"Package.Class"` (`"Engine.KismetStringLibrary"`) |
| `BR.raw.ptr(obj)` / `BR.raw.obj(bytes)` | a UObject as 8 pointer bytes and back |
| `BR.raw.bool`, `BR.raw.i32`, `BR.raw.ivec(x, y, z)` | small codecs |
| `BR.raw.fstring(bytes)` / `BR.raw.ftext(bytes)` | decode FString / FText bytes to UTF-8 |
| `BR.raw.new_fstring(text)` | FString bytes for `text`, its buffer on the game heap (for a parameter the engine frees) |
| `BR.raw.take_handles(array)` | the 8-byte brick handles in a returned TArray's 16 bytes, freeing its buffer (a copy nothing else frees) |

Under it are the native helpers every mod has (from the BrickadiaBridge C++ mod):

| | |
|--|--|
| `__fn_layout(path)` | a UFunction's parameter offsets and sizes |
| `__raw_call(target, path, bytes)` | call it with a raw parameter buffer; returns the buffer after the call |
| `__addr(obj)` / `__obj(addr)` | UObject to address and back |
| `__fname(text)` | an FName as an integer |
| `__peek(addr, len)` | read memory |
| `__alloc(bytes)` / `__free(addr)` | scratch memory the engine only reads during a call |
| `__game_alloc(bytes)` | memory in the game's heap (GMalloc), for things the engine takes over and frees |
| `__game_free(addr)` | free game-heap memory: `__game_alloc` blocks, or an engine container's old buffer |
| `__poke(addr, bytes)` | write memory |
| `__on_call(path, fn)` | raw ProcessEvent hook (`BR.event.hook` wraps it) |
| `__on_tick(fn)` | `fn(deltaSeconds)` every engine tick (`BR.event.tick` wraps it) |
| `__component_data(handle)` | address of a component's data from its 8-byte handle, or nil |
| `__bridge_listen(name, fn)` / `__bridge_send(conn, line)` | the omegga socket ([interop.md](interop.md#transport)) |

Raw-call buffers are never destructed: FString and TArray results leak a little memory per
call, which is fine for occasional use but not for per-tick loops. Typings for all of this are
in [`types/omegga.lua`](../types/omegga.lua) ([editor completion](#editor-completion)).

```lua
-- a brick's colour: GetColor returns an FColor (bytes B, G, R, A)
local lib = StaticFindObject("/Script/Brickadia.Default__BRLuauBrickLibrary")
local b, g, r, a = string.byte(BR.raw.call(lib, "BRLuauBrickLibrary", "GetColor", { Self = handle }).ReturnValue, 1, 4)
```

`__peek` and a wrong layout can crash the server; test new calls on a scratch server
([exploring.md](exploring.md)).
